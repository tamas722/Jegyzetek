# 1. Hibatűrési minták áttekintése és a hibaészlelés (Failure Detection)

## A szerveroldali reziliencia szerepe

A cloud-native tervezés a **design for failure** alapelvet követi: míg a kliensoldali hibatűrő minták a hibásan működő szerverek kezelésére készítik fel a hívó felet, addig a szerveroldali reziliencia-minták abban segítenek, hogy a szerver túlélje a túlterhelést, a hibásan viselkedő klienseket és az infrastruktúra dinamikus változásait.

### A kliens- és szerveroldali minták rendszerezése feladatkör szerint

| Feladatkör | Kliensoldali minták (Client-side) | Szerveroldali minták (Server-side) |
|---|---|---|
| **Hibaészlelés (Failure detection)** | Állapotellenőrzések (Health checks) | Állapotellenőrzések (Health checks) |
| **Hibakezelés (Failure mitigation)** | Időkorlát (Timeout), Újrapróbálkozás (Retry), Áramkör-megszakító (Circuit-breaking) | Redundancia (Redundancy), Kecses leállás (Graceful shutdown) |
| **Túlterhelés-megelőzés (Overload prevention)** | Sebességkorlátozás (Rate-limit), Pergésmentesítés (Debounce) | Sebességkorlátozás (Rate-limit), Terheléseldobás (Load-shedding) |

## A Health Check minta (Állapotellenőrzés)

A szerverleállások kezelésének előfeltétele a hibák időben történő észlelése. A **health check** egy dedikált API végpont (gyakori elnevezések: `/health` vagy `/healthz`), amelyen keresztül a terheléselosztók, a monitorozó rendszerek vagy maga a Kubernetes lekérdezheti, hogy az adott szolgáltatáspéldány működőképes-e:

- **HTTP 200 OK:** A replika egészséges és készen áll a kérések fogadására.
- **HTTP 503 Service Unavailable:** A szolgáltatáspéldány nem működőképes.
- **HTTP 429 Too Many Requests:** Fejlettebb implementációkban figyelmeztető jelzés arra, hogy a szerver a kapacitása határán vagy afelett működik.

## A Health Check három szintje

Attól függően, hogy milyen mélységben vizsgáljuk a szolgáltatás működőképességét, három típust különböztetünk meg:

- **Liveness check (Életjel-ellenőrzés):** Csak azt igazolja, hogy a szerverfolyamat fut, elérhető a hálózaton (a tűzfalak és biztonsági szabályok rendben vannak), és képes fogadni az állapotellenőrző kéréseket – arról azonban nem ad információt, hogy a normál üzleti API-hívásokat is ki tudja-e szolgálni.
- **Shallow health check (Sekély ellenőrzés):** A helyi erőforrások rendelkezésre állását teszteli: ellenőrzi a memóriát, a CPU-t, a helyi adatbázis-kapcsolatokat, a lemezterületet és jogosultságokat (lemezhiba kiszűrése), valamint a háttérben futó segédfolyamatok (pl. monitorozó vagy frissítő démonok) meglétét.
- **Deep health check (Mély ellenőrzés):** A szolgáltatás tényleges üzleti funkciójának elvégzését vizsgálja az összes alsóbb szintű (downstream) erőforrás és mikroszolgáltatás kipróbálásával (például a Sales szolgáltatás ellenőrzi a Catalog, a Billing és a Warehouse szolgáltatásokat). Mivel költséges és hajlamos a téves riasztásokra (false positives), három tervezési szabályt kell betartani:
  1. Csak a közvetlen függőségeket teszteljük (a tranzitív függőségeket – például az adatbázist – a közvetlen függőségek saját mély ellenőrzése vizsgálja).
  2. A függőségeket párhuzamosan (concurrently) kérdezzük le.
  3. Ugyanazokat a kliensoldali reziliencia-beállításokat (timeout, retry, circuit breaker) használjuk az ellenőrzéshez, mint egy valódi API-hívásnál.

## Miért a Kubernetes végzi az állapotellenőrzést? ($n^2$ probléma)

Ha minden klienspéldány külön-külön figyelné az összes szerverpéldány állapotát, akkor $n$ kliens és $n$ szerver esetén $n^2$ darab különálló health check terhelné a hálózatot – ez éles környezetben könnyen eléri a teljes hálózati forgalom két számjegyű százalékát, és önmagában is kaszkádolt hibákhoz vezethet. Ehelyett a Podok csak implementálják a `/healthz` végpontot (például egy külön `:8086`-os porton), és maga a Kubernetes végzi a lekérdezéseket: a hibás Podokat azonnal kiveszi a load balancer poolból, majd automatikusan újraindítja őket.

## Kubernetes Probe típusok és konfigurációs paraméterek

A Kubernetes háromféle próbát (probe) biztosít a Podok életciklusának kezelésére:

- **`livenessProbe`:** Folyamatosan ellenőrzi, hogy él-e a konténer; hiba esetén újraindítja a Podot.
- **`startupProbe`:** Lassan induló szolgáltatásokhoz használjuk (például amikor a kvstore egy hatalmas tranzakciós naplóból állítja vissza a memóriát induláskor). Amíg a `startupProbe` nem jelez sikert, a Kubernetes nem futtatja a `livenessProbe` és `readinessProbe` ellenőrzéseket, így megakadályozza, hogy a rendszer idő előtt lelője a még inicializálódó Podot.
- **`readinessProbe`:** A sekély és mély ellenőrzéseket valósítja meg; ha sikertelen, a Pod `0/1 READY` állapotba kerül, és nem kap forgalmat a Service-től, de nem indul újra.

A próbák főbb időzítési paraméterei:

- **`initialDelaySeconds`:** Ennyi másodpercet vár a konténer indulása után az első ellenőrzésig.
- **`periodSeconds`:** Milyen időközönként ismételje az ellenőrzést.
- **`timeoutSeconds`:** Mennyi idő után minősül időtúllépés miatt sikertelennek a próba.
- **`failureThreshold`:** Ennyi egymást követő hiba után tekinti a Podot hibásnak.
- **`successThreshold`:** Ennyi egymást követő sikeres próba után tekinti újra egészségesnek a Podot.

```yaml
# Lassan induló szolgáltatás védelme startupProbe és livenessProbe segítségével
apiVersion: v1
kind: Pod
metadata:
  name: healthcheck
  labels: { app: healthcheck }
spec:
  containers:
  - name: healthcheck
    image: localhost/healthcheck
    imagePullPolicy: Never
    ports:
    - containerPort: 8086
    livenessProbe:
      httpGet: { path: /healthz, port: 8086 }
      periodSeconds: 2
    startupProbe:
      httpGet: { path: /healthz, port: 8086 }
      initialDelaySeconds: 30 # 30 másodpercet hagy az inicializálásra
```

# 2. Szerveroldali hibakezelés: Kecses leállás (Graceful Shutdown)

## Miért szüntet meg a Kubernetes egészséges Podokat?

A Kubernetes éles üzemben is bármikor leállíthat hibátlanul működő Podokat:

- **Visszaskálázáskor (scaling down):** Ha csökken a terhelés, a rendszer törli a felesleges replikákat.
- **Gördülő frissítéskor (rolling update):** Az új verzióra való átálláskor fokozatosan leállítja a régi Podokat és elindítja az újakat.
- **Erőforráshiány esetén:** Ha egy node kifogy a memóriából vagy CPU-ból, a Kubernetes leállítja a rajta futó Podokat.

Ha a szerver leállításkor azonnal elvágja az élő kapcsolatokat, a kliensek hibaként érzékelik a megszakadt kéréseket, és újrapróbálkozási vihart (retry storm) indíthatnak el.

## A leállási folyamat és a Go implementáció buktatói

Amikor a Kubernetes törölni kíván egy Podot, először egy **SIGTERM** szignált küld a folyamatnak, majd megvárja a türelmi időt (grace period), mielőtt kényszerítve (**SIGKILL**) lelőné. A kecses leálláshoz az alkalmazásnak öt feladatot kell elvégeznie:

1. Fogadni a SIGTERM (és helyi fejlesztésnél a SIGINT) szignált.
2. Lecsorgatni (drain) az összes folyamatban lévő klienskérést (új kéréseket már nem fogad, de a megkezdetteket befejezi).
3. Felszabadítani az összes lefoglalt erőforrást (adatbázis-kapcsolatok, goroutine-ok, csatornák).
4. Naplózni az esetleges leállási hibákat.
5. Önként kilépni, amint a leállás befejeződött.

A Go implementáció felépítése során három tipikus hibát kell elkerülni:

- **`http.ErrServerClosed` kezelése:** A `ListenAndServe()` leállításkor mindig `http.ErrServerClosed` hibával tér vissza – ezt az `!errors.Is(err, http.ErrServerClosed)` feltétellel ki kell szűrni, hogy ne tekintsük valódi hibának.
- **`s.Close()` vs. `s.Shutdown(ctx)`:** A `s.Close()` azonnal lezárja az aktív kapcsolatokat, ezért helyette a `s.Shutdown(ctx)` metódust kell használni, amely egy `context.WithTimeout` időkorláton belül megvárja a futó HTTP kérések befejezését.
- **A főszál blokkolása (kritikus sorrend):** Ha a `s.Shutdown(ctx)`-et egy külön goroutine-ból hívjuk meg, az azonnal feloldja a `main()` függvényben blokkoló `s.ListenAndServe()` hívást, így a program kilép, mielőtt a `Shutdown()` befejezhetné a kérések kiszolgálását. A megoldás: a `s.ListenAndServe()`-et kell goroutine-ban indítani, a `main()` főszálát pedig a `<-sigChan` csatornán blokkolni.

```go
package main

import (
	"context"
	"errors"
	"log"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	s := &http.Server{Addr: ":8080"}
	http.Handle("/", http.FileServer(http.Dir("./www")))

	// 1. A HTTP szerver indítása háttér-goroutine-ban
	go func() {
		if err := s.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
			log.Fatalf("HTTP server error: %v", err)
		}
	}()

	// 2. A főszál blokkolása leállítási szignál (SIGINT / SIGTERM) érkezéséig
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)
	<-sigChan

	// 3. Folyamatban lévő kérések kecses befejezése legfeljebb 10 másodpercen belül
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	if err := s.Shutdown(ctx); err != nil {
		log.Fatalf("Shutdown error: %s", err)
	}
}
```

> (Megjegyzés: Az előadás 21–22. diáján lévő kódrészletben elírásként lemaradt a `!` operátor az `errors.Is(err, http.ErrServerClosed)` elől, a 19. dián szereplő `!errors.Is(...)` forma a helyes. Ha a szervernek hosszú ideig tartó műveleteket kell lezárnia, a Kubernetes Pod definícióban érdemes megnövelni a türelmi időt: `terminationGracePeriodSeconds: 600`.)

# 3. Szerveroldali túlterhelés-megelőzés (Overload Prevention)

## 1. Load Shedding (Terheléseldobás)

A load shedding célja, hogy amikor a szerver megközelíti a teljesítőképessége határát (telítettség), a beérkező forgalom egy részét azonnal elutasítsa (jellemzően **HTTP 429 Too Many Requests** válasszal), így megelőzi a teljes összeomlást és a health checkek meghiúsulását.

A `WithLoadShedding` dekorátor egy mutex-szel védett számlálóval követi az egyidejűleg futó kérések számát, és ha az eléri a `threshold` küszöböt, azonnal hibával tér vissza:

```go
// WithLoadShedding korlátozza az egyidejűleg futó hívások maximális számát.
func WithLoadShedding(f Closure, threshold int) Closure {
	counter := 0
	var lock sync.Mutex

	return func() error {
		lock.Lock()
		if counter >= threshold {
			lock.Unlock()
			return fmt.Errorf("too many requests: %d >= %d", counter, threshold)
		}
		counter++
		lock.Unlock()

		err := f()

		lock.Lock()
		counter--
		lock.Unlock()
		return err
	}
}
```

## 2. Rate Limiter / Throttling (Sebességkorlátozás)

A rate-limiter korlátozza, hogy egy függvényt vagy végpontot időegységenként legfeljebb hányszor lehet meghívni (például másodpercenként legfeljebb 10 kérés, vagy 24 órán belül legfeljebb 3 sikertelen bejelentkezés).

**Debounce vs. Rate Limiter:** Míg a debounce az összetorlódott híváshullámokra (burst) koncentrál (hogy egy hullámon belül csak egyszer fusson le a hívás), addig a rate-limiter a hosszabb időtávú átlagsebességet korlátozza, miközben kis mértékű lökésszerű forgalmat (burst) átenged.

**Token Bucket (Zsetonvödör) algoritmus:** Egy legfeljebb `Capacity` darab zsetont befogadó vödörbe minden `Period` időtartam után `Fill` darab új zseton kerül. Minden beérkező kérés kivesz egy zsetont; ha a vödör üres (`tokens <= 0`), a kérés elutasításra kerül.

A Go implementációban két fontos technikai részletre kell figyelni:

- **A háttér-goroutine leállítása (`context.Context`):** A zsetonokat újratöltő `time.NewTicker` egy végtelen ciklusú háttér-goroutine-ban fut, ezért a `WithRateLimiter` paraméterként átvesz egy `ctx` kontextust, amellyel leállítható a goroutine és elkerülhető az erőforrás-szivárgás.
- **Szálbiztonság (`sync/atomic`):** Mivel a `tokens` változót egyszerre módosítja a háttérben futó újratöltő goroutine és a kéréseket kiszolgáló szálak, szinkronizálni kell. Primitív típusoknál (pl. `int32`, `bool`) mutex helyett a `sync/atomic` csomag `atomic.Int32` típusát használhatjuk.

```go
type RateLimiter struct {
	Capacity int32         // A vödör maximális kapacitása (megengedett burst)
	Fill     int32         // Egy periódus alatt betöltött zsetonok száma
	Period   time.Duration // Az újratöltés időközének hossza
}

func WithRateLimiter(ctx context.Context, f Closure, r RateLimiter) Closure {
	var tokens atomic.Int32
	tokens.Store(r.Capacity)
	ticker := time.NewTicker(r.Period)

	// Zsetonok periodikus újratöltése a háttérben
	go func() {
		defer ticker.Stop()
		for {
			select {
			case <-ctx.Done():
				return // Szivárgásmentes kilépés kontextus leállításakor
			case <-ticker.C:
				for {
					curr := tokens.Load()
					next := curr + r.Fill
					if next > r.Capacity {
						next = r.Capacity
					}
					if tokens.CompareAndSwap(curr, next) {
						break
					}
				}
			}
		}
	}()

	return func() error {
		// Atomi zsetonlevonás Compare-And-Swap ciklussal
		for {
			curr := tokens.Load()
			if curr <= 0 {
				return errors.New("too many calls")
			}
			if tokens.CompareAndSwap(curr, curr-1) {
				return f()
			}
		}
	}
}
```

> (Megjegyzés a szálbiztonsághoz: az előadás 30. diája az `atomic.Int32` `.Load()` és `.Store()` metódusait említi; éles párhuzamos környezetben a kiolvasás és a csökkentés közötti versenyhelyzet elkerüléséhez a fenti `CompareAndSwap` ciklus teszi valóban atomivá a zsetonkivételt.)

# 4. Összegző tervezési tanulságok

- **Kliens- és szerveroldali minták szinergiája:** A kliensoldali minták (timeout, retry, circuit breaker) és a szerveroldali mechanizmusok (health check, graceful shutdown, load shedding, rate-limiter) együttesen teszik lehetővé, hogy a mikroszolgáltatások túléljék mind a függőségeik hibáit, mind a hirtelen terhelési csúcsokat.
- **Zökkenőmentes Kubernetes életciklus:** A megfelelően beállított állapotellenőrzések (probes) és a kecses leállás (graceful shutdown) révén a Kubernetes észrevétlenül hajthatja végre a fel- és leskálázásokat, valamint a gördülő frissítéseket anélkül, hogy a kliensek hibát érzékelnének.
- **Az állapotmentesség feltétele:** Mindez csak akkor működik adatvesztés nélkül, ha a korábbi előadásokon tanultak szerint a Podok belső állapotát megfelelően kezeltük – például kiszerveztük egy külső, perzisztens adattárolóba.
