# 1. Idempotencia és a párhuzamos állapotmódosítás problémája

## Hol tartunk most? Kliensoldali kompozíció (get-set)

A Leaderboard alkalmazásunkat két különálló mikroszolgáltatásra bontottuk szét: egy állapotmentes HTTP frontendre (amely kiszolgálja a statikus HTML/JS felületet, valamint a `getScores` és `addScore` végpontokat) és egy külső kulcs-érték tárra (key-value store), amely az erőforrás-állapotot tárolja. Annak érdekében, hogy elkerüljük a szoros csatolást, az adattároló csak két generikus műveletet kínál (`get(key)` és `set(key, value)`), az összetettebb műveleteket (növelés, csökkentés, két kulcs értékének összeadása) pedig a kliens rakja össze (**client-side composition**): lekéri az értéket, helyben módosítja, majd visszamenteni a `set` hívással. Ez a minta azonban párhuzamos írások esetén súlyos adatvesztéshez vezet.

## A versenyhelyzet reprodukálása lokálisan (`code/adder`)

Cloud-native alaprecept, hogy egy Kubernetesben jelentkező elosztott problémát először egy minimális, elszigetelt helyi Go programmal reprodukálunk, amelyben goroutine-ok modellezik a párhuzamosan futó podokat. Az alábbi példában (`adder_unsafe.go`) 20 goroutine mindegyike 100-szor növeli meg egy közös számláló értékét a `get()` és `set()` műveletek kombinálásával, a főszál pedig a `sync.WaitGroup` (`wg.Add(20)`, `wg.Done()`, `wg.Wait()`) segítségével várja meg az összes szál befejezését:

```go
package main

import (
	"fmt"
	"sync"
)

var counter int
var mu sync.RWMutex

func get() int {
	mu.RLock()
	defer mu.RUnlock()
	return counter
}

func set(x int) {
	mu.Lock()
	defer mu.Unlock()
	counter = x
}

func main() {
	var wg sync.WaitGroup
	wg.Add(20) // 20 goroutine-ra fogunk várni

	for i := 0; i < 20; i++ {
		go func() {
			for j := 0; j < 100; j++ {
				c := get() // 1. Kiolvasás
				c += 1     // 2. Helyi növelés
				set(c)     // 3. Visszaírás
			}
			wg.Done() // Jelzi, hogy a szál végzett
		}()
	}

	wg.Wait()            // Megvárja, amíg a számláló 0-ra csökken
	fmt.Println(counter) // Várt érték: 2000, valóság: pl. 489!
}
```

Miért lesz az eredmény 2000 helyett például 489? Bár külön-külön a `get()` és a `set()` is zárolva van egy `sync.RWMutex`-szel, a teljes „kiolvas–módosít–visszaír” (read-modify-write) műveletsor **nem atomi**. Ha két szál egyszerre hívja meg a `get()` függvényt és mindkettő `x` értéket olvas ki, akkor utána mindkettő `x + 1`-et ír vissza a `set()` hívással – így a számláló `x + 2` helyett csak `x + 1`-re nő, és az egyik növelés elveszik (**lost update**).

## Megoldás: Verziózott értékek (Leslie Lamport trükkje)

A problémát az elosztott rendszerek egyik úttörője, Leslie Lamport által javasolt **verziózott értékek** (versioned values, más néven optimista konkurencia-vezérlés) technikájával oldjuk meg:

- Minden tárolt érték mellé elmentünk egy egyszerű egész verziószámot (`version`) is.
- A `get(key)` hívás az érték mellett visszaadja az aktuális verziószámot is.
- A módosító művelet – amelyet a nem biztonságos `set`-től való megkülönböztetésül `put(key, value, version)` névre keresztelünk át – paraméterként megkapja a kliens által utoljára ismert verziószámot is.
- A `put` kizárólag akkor hajtja végre az írást, ha a kliens által küldött verziószám megegyezik az adatbázisban tárolt verziószámmal; ilyenkor beírja az új értéket és eggyel megnöveli a verziószámot (`version += 1`).
- Ha közben egy másik kliens már módosította az adatot, a verziószámok eltérnek, a `put` hibával visszatér, a kliens pedig újraolvassa a friss adatot és újrapróbálja (retry) a műveletet.

```go
// Biztonságos, verziózott számláló (adder_safe.go)
var counter, version int
var mu sync.RWMutex

func get() (int, int) {
	mu.RLock()
	defer mu.RUnlock()
	return counter, version
}

func put(x, v int) error {
	mu.Lock()
	defer mu.Unlock()
	if v != version {
		return fmt.Errorf("put: version mismatch: %d != %d", v, version)
	}
	counter = x
	version += 1
	return nil
}

// Kliensoldali újrapróbálkozó ciklus:
// for {
//     c, v := get()
//     c += 1
//     if put(c, v) == nil {
//         break
//     }
// }
```

(Érdekesség: a modern Intel processzorok ezt a tranzakciós memória szemléletet hardveres szinten is megvalósítják a CPU-ban.)

## Az idempotencia fogalma és matematikai háttere

A cloud-native rendszerek egyik legfontosabb tervezési mintája, hogy a sikertelen API-kéréseket addig próbáljuk újra (retry), amíg sikerrel nem járnak. Ez azért működik biztonságosan, mert mind a `get`, mind a verziózott `put` művelet **újrapróbálható (retriable)**: ha például egy `put(c, v)` kérés válasza elveszik a megbízhatatlan hálózaton, a kliens időtúllépés (timeout) után nyugodtan újraküldheti ugyanazt a kérést, az eredmény pontosan ugyanaz marad.

**Idempotencia (absztrakt algebrai definíció):** Egy $\times$ művelet akkor idempotens, ha bármely $x$ elemre teljesül, hogy

$$
x \times x = x,
$$

vagyis többszöri alkalmazása ugyanazt az eredményt adja, mint az egyszeri végrehajtás.

**Idempotens példák:** az abszolútérték ($\vert{}\vert{}x\vert{}\vert{} = \vert{}x\vert{}$), a padló- és plafonfüggvény ($\lceil\lceil x \rceil\rceil = \lceil x \rceil$), a `get` és a verziózott `put`, valamint a deklaratív konfigurációk, mint a `kubectl apply`.

**Nem idempotens példák:** az alapvető aritmetikai műveletek (`+`, `-`) vagy a verzió nélküli `incr`.

**Kapcsolódó algebrai tulajdonságok:** Elosztott rendszerekben (például CRDT adatszerkezeteknél) gyakran megköveteljük a kommutativitást ($x \times y = y \times x$, hogy a műveletek érkezési sorrendje ne számítson) és az asszociativitást ($x \times (y \times z) = (x \times y) \times z$, hogy a csoportosítás lényegtelen legyen) is.

# 2. A verziózott kulcs-érték tár (kvstore) és integrációja

## Adatmodell és a teljesen idempotens put művelet

A `code/kvstore` szolgáltatásban minden kulcs-érték párhoz külön verziószámot tárolunk (ha egyetlen globális verziószám lenne az egész adatbázisra, a különböző kulcsokat módosító kliensek is blokkolnák egymást, ami rosszul skálázódna):

```go
type VersionedValue struct {
	Value   string `json:"value"`
	Version int    `json:"version"`
}

type VersionedKeyValue struct {
	Key            string `json:"key"`
	VersionedValue        // Struktúra beágyazása (Promotion)
}

var store = make(map[string]VersionedValue)
var mu sync.RWMutex
```

A `put` függvény implementációjában van egy kritikus finomság, amely teljesen idempotenssé teszi a hívást:

```go
func put(key string, v VersionedValue) error {
	mu.Lock()
	defer mu.Unlock()

	val, ok := store[key]
	if !ok {
		// 1. Új kulcs létrehozása: a verziószámot 1-re inicializáljuk
		v.Version = 1
		store[key] = v
		return nil
	}

	if val.Value == v.Value {
		// 2. Ugyanazon érték ismételt írása verziószámtól függetlenül sikeres!
		// Ha az első kérés sikeres volt, de a válasz elveszett, a retry nem dob hibát.
		return nil
	}

	if val.Version != v.Version {
		// 3. Verzióütközés: időközben más már módosította a kulcsot
		return fmt.Errorf("put: version mismatch: %d != %d", val.Version, v.Version)
	}

	// 4. Sikeres frissítés és verzió növelése
	val.Value = v.Value
	val.Version += 1
	store[key] = val
	return nil
}
```

## A kvstore HTTP szerver és a tranzakciós napló beépítése

A kulcs-érték tár a `:8081`-es porton figyel, és három végpontot kínál (`/api/get`, `/api/put`, `/api/list`). (Szemantikailag a `/api/put` végponthoz HTTP PUT metódust vagy `Idempotency-Key` fejlécet illik használni az idempotencia jelzésére, az előadás az egyszerűség kedvéért POST-ot használ.) Verzióütközés esetén a szerver **HTTP 428 Precondition Required** státuszkóddal válaszol.

Annak érdekében, hogy a kvstore újraindításkor se veszítse el az adatait, beépítjük a korábban megírt `transactionlog` csomagot (`go mod edit -replace transactionlog=../transactionlog && go mod tidy`):

- Csak az állapotmódosító `put` műveleteket naplózzuk (a `get` és a `list` csak olvas, nincs mellékhatásuk).
- Induláskor az `initTransactionLog()` visszaállítja a memóriabeli `store` mapet a `/tmp/translog.log` fájlból, majd a `logger.Run(context.Background())` elindítja a háttérírót.
- A `/api/put` handlerben sikeres `put(...)` hívás (`err == nil`) után JSON formátumban elküldjük a `VersionedKeyValue` rekordot a naplónak: `logger.Write("put", ...)`. (Megjegyzés: a 20. dián szereplő pszeudokódban elírásként `err != nil` szerepel, de a naplózásnak nyilvánvalóan sikeres íráskor, tehát `err == nil` esetén kell megtörténnie.)

## A Leaderboard átállítása a kvstore használatára és telepítés Kubernetesbe

A Leaderboard `pkg/db/kvstore` implementációjában az `Add(score)` metódus egy végtelen újrapróbálkozó ciklusban kommunikál a kulcs-érték tárral:

```go
for {
	// 1. Aktuális érték és verzió lekérdezése
	r, err := http.Post(db.url+"/api/get", "application/json", /* JSON encoded name */)
	if err != nil || r.StatusCode != http.StatusOK {
		continue // Hálózati vagy HTTP hiba esetén újrapróbálkozás
	}
	vValue := /* decode VersionedValue from response */

	// 2. Pontszám növelése helyben
	vValue.Value += score.Points

	// 3. Visszaírás a kiolvasott verziószámmal
	r, err = http.Post(db.url+"/api/put", "application/json", /* JSON encoded VersionedKeyValue */)
	if err != nil || r.StatusCode != http.StatusOK {
		continue // Verzióütközés (428) vagy hiba esetén újrakezdés elölről!
	}
	break // Sikeres mentés: kilépés a ciklusból
}
```

**Telepítés Kubernetesbe:**

- A kvstore könyvtárban le kell futtatni a `go mod vendor` parancsot, hogy a helyi `transactionlog` függőség bekerüljön a konténerépítési környezetbe, majd megépítjük a `localhost/kvstore` és a `localhost/leaderboard` konténerképeket.
- A `kubectl apply -f deploy/kubernetes-kvstore-db.yaml` elindítja a két szolgáltatást: a Leaderboardot külső LoadBalancer Service-en (`:8080`), a kvstore-t pedig belső Service-en (`:8081`) egy PersistentVolume kötettel megtámogatva.
- Ha a Leaderboardot 3 replikára skálázzuk (`kubectl scale deployment leaderboard --replicas=3`), majd mindkét Deploymentet újraindítjuk (`kubectl rollout restart`), az adatok maradéktalanul megmaradnak és minden pod számára konzisztensek.

# 3. Laza csatolás magasabb szinten (Loose Coupling Revisited)

A generikus adatmodellek és az idempotens API-k önmagukban még nem oldják meg a hosszú távú karbantarthatóságot; három további iparági eszköz segít felszámolni a komponensek közötti csatolást:

## 1. API verziózás (API Versioning)

A törékeny adatcsere-protokollok (fragile exchange protocols) elkerülésére szolgál, amikor egy meglévő szolgáltatás adatstruktúráját bővíteni kell anélkül, hogy a régi klienseket eltörnénk.

**Esettanulmány (LRU gyorsítótár):** Tegyük fel, hogy a kvstore-t egy SQL adatbázis előtti gyors LRU (Least Recently Used) gyorsítótárként is használni akarjuk, amely megteléskor a legrégebben módosított elemet dobja ki. Ehhez tárolnunk kell az utolsó módosítás időbélyegét (`Timestamp int` UNIX epoch időben) is.

**Megoldás:** Minden API struktúrába felveszünk egy `APIVersion` mezőt (`json:"api"`), a szerver belső tárolóját átállítjuk a legújabb formátumra (`apiv2.AgedVersionedValue`), és egyszerre két végpontot (`/api/v1/get` és `/api/v2/get`) publikálunk. A régi v1 végpont belül lekéri a v2 adatot, majd egy konverziós függvénnyel (`ConvertV2ToV1`) átalakítja a régi formátumra:

```go
// pkg/api/v1
type VersionedValue struct {
	APIVersion string `json:"api"` // "v1"
	Value      string `json:"value"`
	Version    int    `json:"version"`
}

// pkg/api/v2
type AgedVersionedValue struct {
	APIVersion string `json:"api"` // "v2"
	Value      string `json:"value"`
	Version    int    `json:"version"`
	Timestamp  int    `json:"timestamp"`
}

// Konverzió v2-ről v1-re (eldobja a Timestamp mezőt):
func ConvertV2ToV1(source v2.AgedVersionedValue) v1.VersionedValue {
	return v1.VersionedValue{
		APIVersion: "v1",
		Value:      source.Value,
		Version:    source.Version, // Ez az adat verziója (optimista zároláshoz), NEM az APIVersion!
	}
}
```

## 2. API csoportosítás (API Grouping)

Hatalmas rendszereknél (mint a Kubernetes API) egyetlen hatalmas API verziószámának emelése és az összes konverziós függvény megírása kezelhetetlen lenne. Ehelyett „oszd meg és uralkodj” alapon API csoportokra osztjuk az interfészt, és minden csoportot külön verziózunk. A Kubernetes YAML fájlok elején látható `apiVersion: apps/v1` pontosan ezt jelenti (`apps` az API csoport neve, `v1` pedig annak stabil verziója):

- **core** (üres csoportnév, `v1`): Alapvető erőforrások, mint a Pod és a Service.
- **apps** csoport (`apps/v1`): Összetettebb munkaterhelések, mint a Deployment és a StatefulSet.
- **batch** csoport (`batch/v1`): Kötegelt feladatok, mint a Job és a CronJob.

## 3. OpenAPI specifikáció és automatikus kódgenerálás

A HTTP/JSON kérések és válaszok kézi szerializálása (Marshal/Unmarshal) és validálása ismétlődő, unalmas feladat. Az OpenAPI egy szabványos YAML vagy JSON alapú leírónyelv REST API-k dokumentálására, vizualizálására és automatizálására:

- **Előnyei („loose coupling on steroids”):** A specifikációból automatikusan generálható a kliens- és szerveroldali Go kód, automatikusan validálja a bejövő adatokat (pl. `minimum: 0`), interaktív dokumentációt készít, sőt a szerver publikálhatja a saját OpenAPI leíróját, így a kliensek futásidőben is felfedezhetik a végpontokat.
- **Go eszköztipp:** Ne a hivatalos Swagger kódgenerátort használd (idegen, nem idiomatikus Go kódot generál), hanem a `github.com/oapi-codegen/oapi-codegen` modult, amely tiszta, idiomatikus Go kódot állít elő az `operationId` mezők alapján.

```yaml
openapi: 3.0.3
info:
  title: REST API for the kvstore key-value store.
  version: 1.0.0
paths:
  /api/get:
    post:
      summary: GET value and version for the given key.
      operationId: opGet # Ehhez a névhez rendeli a generátor a Go függvényt
      requestBody:
        required: true
        content:
          application/json:
            schema: { type: string }
      responses:
        "200":
          description: Successful operation
          content:
            application/json:
              schema: { $ref: '#/components/schemas/versionedKeyValue' }
components:
  schemas:
    versionedKeyValue:
      type: object
      properties:
        value: { type: string }
        version: { type: integer, format: int64, minimum: 0 } # Automatikus validáció!
```

A Kubernetes API szerver maga is egy OpenAPI specifikációval van leírva, amelyet a `kubectl proxy --port=8080 &` elindítása után a `curl http://localhost:8080/openapi/v3/api/v1 | jq` paranccsal bármikor lekérdezhetsz.

# 4. Összegző tervezési tanulságok

- **Állapotmentesség és perzisztencia együttese:** Az immutability megköveteli, hogy az alkalmazás állapotmentes legyen – a state externalization biztosítja, hogy minden Pod konzisztens képet lásson, a persistence pedig megőrzi az adatokat újraindításkor.
- **Hibatűrő, laza csatolású kommunikáció:** Az idempotens API-k lehetővé teszik a sikertelen hálózati kérések biztonságos újrapróbálását, míg az API verziózás, az API csoportosítás és az OpenAPI sémák függetlenné teszik egymástól a szolgáltatások fejlesztési életciklusát.
- **Az absztrakciós réteg áthelyezése:** A state externalization valójában egy új absztrakciós szintre emeli a problémát: most már nem a Leaderboard, hanem maga a kvstore az az egyetlen állapottartó komponens, amelyet még nem tudunk több Podra skálázni – de legalább az erőforrás-állapot már explicit és jól elkülönített, ahelyett, hogy a Podok memóriájában rejtőzködne.
