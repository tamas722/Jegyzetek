# 1. A skálázhatóság alapjai és az erőforrás-kezelés (Scalability)

## Miért van szükség dinamikus skálázásra?

A szolgáltatásokra érkező terhelés időben folyamatosan ingadozik: nappal jellemzően magasabb, éjszaka alacsonyabb, emellett váratlan események (például egy virálissá váló bejegyzés vagy egy sportesemény) akár 100–1000-szeres forgalmi csúcsokat (usage spikes) is okozhatnak. Ha egy rendszert a csúcsterhelésre méretezünk, éjszaka feleslegesen pazarolja az erőforrásokat; ha pedig az átlagos vagy éjszakai terhelésre építjük, a csúcsidőszakban összeomlik.

A **skálázhatóság (scalability)** a rendszer azon képessége, hogy a terhelés jelentős növekedése vagy csökkenése mellett is ellássa a feladatát, két fő cél mentén:

- **Rendelkezésre állás maximalizálása:** A rendszer leköveti a terhelési csúcsokat (scale-up / scale-out), így a felhasználók folyamatosan működőképes szolgáltatást érzékelnek.
- **Költségek minimalizálása:** A terhelés csökkenésekor felszabadítja a felesleges kapacitásokat (scale-down / scale-in), így mindig csak a szükséges minimum erőforrást használja.

A skálázási technikák alapvetően az erőforrás-állapottól (resource state) függenek: míg az állapotmentes (immutable/stateless) szolgáltatások egyszerű replikációval könnyen skálázhatók, az állapottartó (mutable/stateful) komponensek speciális architektúrát igényelnek.

## Vertikális vs. Horizontális skálázás

| Szempont | Vertikális skálázás (Vertical scaling) | Horizontális skálázás (Horizontal scaling) |
|---|---|---|
| **Elnevezés** | scale-up (növelés) / scale-down (csökkentés) | scale-out (bővítés) / scale-in (szűkítés) |
| **Mechanizmus** | A meglévő Podokhoz rendelt CPU- és memóriakapacitás növelése vagy csökkentése. | Új Pod-példányok hozzáadása vagy meglévők eltávolítása (replikáció). |
| **Korlátok és hatások** | Egyetlen fizikai gép maximális kapacitása behatárolja; Kubernetesben a módosítás újraindítja a Deploymentet (megszakítva az élő kéréseket). | Gyakorlatilag korlátlanul skálázható, növeli a redundanciát és a hibatűrést; a Service egyenletesen osztja el a terhelést. |
| **Állapotkezelés** | Nem igényel feltétlenül állapotmentességet. | Megköveteli az azonos konfigurációjú, állapotmentes (immutable) Podokat. |

> (Megjegyzés: A futó Podok újraindítás nélküli erőforrás-módosítása – in-place resource update – a Kubernetes v1.34-es verziójában még kísérleti funkció.)

## Erőforráskorlátok és QoS osztályok Kubernetesben

Alapértelmezés szerint a Kubernetes a Podokat a **BestEffort** QoS (Quality of Service) osztályba sorolja, ahol a CPU-időt egy közös készletből kapják. Ha ugyanarra a node-ra egy számításigényes szomszédos Pod kerül, az kiéheztetheti a szolgáltatásunkat, ezért a teljesítmény kiszámíthatatlanná válik. A kiszámítható működéshez két paramétert adunk meg a konténer sablonban:

- **`resources.requests`:** A Pod számára kizárólagosan garantált minimális CPU- vagy memóriamennyiség.
- **`resources.limits`:** A maximális CPU- vagy memóriamennyiség, amelyet a Pod felhasználhat (a Kubernetes kikényszeríti a felső korlátot).

> **Bevált gyakorlat:** Érdemes a request és a limit értékét azonosra állítani.

```yaml
# Vertikális skálázás és erőforrás-korlátozás a Deploymentben (100m = 0.1 CPU mag = 10%)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: leaderboard
  labels: { app: leaderboard }
spec:
  selector:
    matchLabels: { app: leaderboard }
  template:
    metadata:
      labels: { app: leaderboard }
    spec:
      containers:
      - name: leaderboard
        image: localhost/leaderboard:latest
        ports: [ { containerPort: 8080 } ]
        resources:
          requests: { cpu: "100m" } # 1 millicore (1m) egy CPU mag 0,1%-a
          limits:   { cpu: "100m" }
```

# 2. Állapotmentes szolgáltatások skálázása (Scaling Immutable Services)

## Terheléses mérés és skálázási törvények (Amdahl törvénye)

Ha a fenti 100m CPU-korláttal futó Leaderboard szolgáltatást (mögötte egyetlen kvstore példánnyal) horizontálisan skálázzuk (`kubectl scale deployment leaderboard --replicas=N`), és 500 feltöltött felhasználó mellett mérjük a `/api/getScores` végpont másodpercenkénti kiszolgálási sebességét (goodput, qps), az elosztott rendszerek egyik alapvető törvényszerűségét figyelhetjük meg: a **csökkenő hozadék elvét (Amdahl törvénye)**.

- Az első néhány Pod hozzáadása közel lineárisan növeli a hasznos áteresztőképességet (goodput: 1 Podnál ~47 qps, 2 Podnál ~116 qps, 3 Podnál ~178 qps).
- A 7. Pod hozzáadása már csak 4–5% többletet ad a lineáris 17% helyett, egy ponton túl pedig a további skálázás már egyáltalán nem javítja (sőt, akár ronthatja is) a teljesítményt.

**A szűk keresztmetszet (bottleneck):** A rendszer maximális teljesítményét mindig a nem skálázható komponens határozza meg. Mivel minden `getScores` kérés egy `list` hívást indít az egyetlen példányban futó kvstore felé, ha a kvstore legfeljebb 500 `list` kérést bír el másodpercenként, akkor a teljes rendszer teljesítménye akkor sem haladja meg az 500 qps-t, ha 100 frontend Podot indítunk.

## Tipikus szűk keresztmetszetek elosztott rendszerekben

- **Soros munkaterhelés (Serial workload):** Egyszálú alkalmazások, horizontálisan nem skálázható állapottartó mikroszolgáltatások, vagy a kritikus szakaszokban (mutex zárak alatt) töltött idő.
- **CPU-korlátos (CPU-bound):** A processzor műveleti sebessége szab határt – könnyen skálázható horizontálisan, mert több Pod több CPU-t jelent.
- **Memóriakorlátos (Memory-bound):** A RAM-ban tartható adatmennyiség korlátozza – szintén jól skálázható horizontálisan.
- **I/O-korlátos (Lemez és hálózat):** A háttértár írási/olvasási sebessége (adatbázisoknál) és a hálózati sávszélesség – ezek skálázása a legnehezebb.

## Automatikus skálázás: Horizontal Pod Autoscaler (HPA)

A kézi `kubectl scale` helyett az **Autoscaling** minta dinamikusan, a valós terheléshez igazítva ad hozzá vagy távolít el Podokat. Kubernetesben ezt a **HorizontalPodAutoscaler (HPA)** erőforrás valósítja meg, amely periodikusan lekérdezi a metrikákat a Kubernetes Metrics Server-től:

```bash
# A Podok számát 1 és 10 között tartja úgy, hogy az átlagos CPU-terhelés 70% körül maradjon:
kubectl autoscale deployment leaderboard --cpu-percent=70 --max=10
```

A HPA a CPU mellett memória-használat, sőt egyedi alkalmazásszintű metrikák (pl. egy Podra jutó aktív kérések száma másodpercenként) alapján is képes skálázni. Fontos, hogy a Kubernetes a skálázáskor nem kezeli a Podok belső állapotát, így az automatikus skálázás előfeltétele a korábban megvalósított állapotmentesség.

# 3. Állapottartó szolgáltatások skálázása (Scaling Mutable Services)

## Sharding (Adatparticionálás)

Ahhoz, hogy a szűk keresztmetszetet jelentő kvstore adatréteget is skálázni tudjuk, **sharding (particionálás)** technikát alkalmazunk, amelynek két fő formája van:

- **Adatalapú particionálás (Data sharding):** Az adatbázis kulcsterét több különálló részre (shard-ra) osztjuk fel, és minden állapottartó Pod csak a saját kulcstartományáért felel.
- **Szerepkör-alapú particionálás (Role-based sharding):** A Redis például a data sharding mellett szerepkörök szerint is bontja a forgalmat: a master csomópontok csak írási (`put`/`set`) kéréseket fogadnak, és replikálják az adatokat a slave csomópontokra, amelyek kizárólag olvasási (`get`) kéréseket szolgálnak ki (a skálázáshoz azonban újraparticionáláskor gyakran újraindítás szükséges).

## Kliensoldali kulcs-hashelés (Key Hashing)

A Leaderboard esetében a felhasználónevek kulcsterét több kvstore Pod között osztjuk szét kliensoldali key-hashing segítségével: minden olvasásnál és írásnál kiszámítjuk a kulcs hash-értékét, majd elosztjuk maradékosan a shardok számával (`hash(key) % num_shards`), így megkapjuk a felelős Pod sorszámát.

Ennek a megközelítésnek négy fő előnye van:

1. Minden kulcs egyértelműen egyetlen adott shardhoz (Podhoz) rendelődik hozzá.
2. Egyenletes kulcseloszlás esetén a terhelés is egyenletesen oszlik meg a Podok között.
3. Magát a kvstore szervert egyáltalán nem kell átírni: a shardok nem is tudják, hogy a kulcstérnek csak egy részét kezelik.
4. A teljes logika kliensoldalon megvalósítható (igaz, a kliens kódja némileg összetettebbé válik).

## A shardedkvstore adatréteg megvalósítása Go-ban

Létrehozzuk a `pkg/db/shardedkvstore` csomagot, amely tárolja a shardok címeit (`urls []string`) és darabszámát (`num int`), a kulcsok leképezéséhez pedig az SHA-1 hash függvényt használja:

```go
package shardedkvstore

import (
	"crypto/sha1"
	"errors"
	"leaderboard/pkg/api"
	"net/http"
	"resilient"
)

type shardedKVStore struct {
	urls []string
	num  int
}

func NewDataLayer(addrs []string) api.DataLayer {
	kv := shardedKVStore{
		urls: make([]string, len(addrs)),
		num:  len(addrs),
	}
	for i := range addrs {
		kv.urls[i] = "http://" + addrs[i]
	}
	return &kv
}

// getShard kiszámítja, melyik shard Pod felel az adott kulcsért.
func (db *shardedKVStore) getShard(key string) int {
	checksum := sha1.Sum([]byte(key))
	hash := int(checksum[7]) // Egy tetszőleges bájt kiválasztása a hash-ből
	return hash % db.num
}

func (db *shardedKVStore) Add(score api.Score) error {
	shard := db.getShard(score.Name) // Csak a célzott sharddal kommunikálunk!

	retrier := resilient.WithRetry(func() error {
		r, err := http.Get(db.urls[shard] + "/api/get?id=" + score.Name)
		if err != nil || r.StatusCode != http.StatusOK {
			return errors.New("get failed")
		}
		// Érték dekódolása és pontszám növelése...
		r, err = http.Post(db.urls[shard]+"/api/put", "application/json", /* JSON */)
		if err != nil || r.StatusCode != http.StatusOK {
			return errors.New("put failed")
		}
		return nil
	}, resilient.DefaultBackoff)

	return retrier()
}
```

> (Megjegyzés: Míg az `Add` csak egyetlen shardot szólít meg, a `List()` metódusnak végig kell iterálnia az összes shard URL-jén, mindegyiktől le kell kérnie a `/api/list` eredményét, majd össze kell fűznie a részeredményeket.)

## Telepítés Kubernetesbe: StatefulSet és Headless Service

A particionált kvstore Podok már nem cserélhetők fel egymással, mert mindegyik más kulcsokat és saját tranzakciós naplót tárol – ezért a Deployment helyett a Kubernetes **StatefulSet** erőforrását használjuk:

- **Egyedi Pod-identitás:** A StatefulSet garantálja a Podok egyedi, kiszámítható elnevezését `<név>-<index>` formában (pl. `kvstore-0`, `kvstore-1`, `kvstore-2`).
- **Különálló tárolók (`volumeClaimTemplates`):** A Kubernetes minden egyes shard Podhoz automatikusan létrehoz egy saját PersistentVolumeClaim-et és PersistentVolume-ot a tranzakciós napló számára.
- **Headless Service (`clusterIP: None`):** Mivel a kliensnek nem egy véletlenszerűen terheléselosztott IP-címre van szüksége, hanem név szerint kell elérnie az egyes shardokat, `clusterIP: None` beállítással ún. headless Service-t hozunk létre. Ez minden Podhoz egyedi belső DNS-nevet regisztrál `<pod-név>.<service-név>` formában (pl. `kvstore-0.kvstore.default.svc.cluster.local`), így a Podok IP-cím ismerete nélkül is közvetlenül megszólíthatók.

```yaml
# StatefulSet és Headless Service a 3 shardból álló kvstore-hoz
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kvstore
  labels: { app: kvstore }
spec:
  serviceName: "kvstore"
  replicas: 3
  selector:
    matchLabels: { app: kvstore }
  template:
    metadata:
      labels: { app: kvstore }
    spec:
      containers:
      - name: kvstore
        image: localhost/kvstore
        ports: [ { containerPort: 8081 } ]
        volumeMounts: [ { name: translog, mountPath: "/tmp" } ]
  volumeClaimTemplates:
  - metadata:
      name: translog
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests: { storage: "5Mi" }
---
apiVersion: v1
kind: Service
metadata:
  name: kvstore
spec:
  selector: { app: kvstore }
  clusterIP: None # Headless Service: közvetlen Pod DNS rekordokat generál
  ports: [ { port: 8081 } ]
```

A Leaderboard `main.go` fájljában ezután a `shardedkvstore.NewDataLayer(...)` konstruktornak átadjuk a három shard DNS-címét (`kvstore-0.kvstore:8081`, `kvstore-1.kvstore:8081`, `kvstore-2.kvstore:8081`), majd újraépítjük a konténerképet. (Megjegyzés: a 28. dián a `NewDataLayer` példahívásában egyetlen vesszővel elválasztott string szerepel a 22. dián definiált `[]string` szelet helyett.) A tesztek igazolják, hogy a sharding csökkenti az 500 pontszám betöltési idejét (9 másodpercről 7 másodpercre), de a maximális sebességhez a frontend Podokat is párhuzamosan fel kell skálázni.

# 4. Összegző tervezési tanulságok

- **Skálázhatóságra tervezés az első perctől:** Tisztán válasszuk szét az állapotmentes és az állapottartó munkaterheléseket – az állapotmentes rétegeket HPA segítségével automatikusan skálázzuk, az állapottartó rétegeket pedig shardinggal particionáljuk.
- **Pontos erőforrás-menedzsment:** A HPA megbízható működéséhez mindig állítsuk be a Podok CPU- és memóriakereteit (`requests` és `limits`).
- **A stateful skálázás korlátai:** Bár a kliensoldali key-hashing és a Kubernetes StatefulSet működőképes megoldást ad, az állapottartó elosztott rendszerek üzemeltetése (különösen a dinamikus shard-hozzáadás és adatátmozgatás) rendkívül összetett feladat, amelyet éles környezetben érdemes menedzselt adatbázis-szolgáltatásokra bízni.
