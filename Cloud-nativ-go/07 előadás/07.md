# 1. Perzisztencia folytatása: Kubernetes kötetek és Vendoring (Persistence cont'd)

## Hol tartunk most?

Az előző előadáson elkészítettük a Leaderboard webalkalmazás perzisztens változatát (`code/leaderboard-trans`), amely egy statikus HTML/JS felület mögött két JSON/HTTP API végpontot (`getScores` és `addScore`) szolgál ki, az erőforrás-állapotot (resource state) pedig egy hozzáfűzhető tranzakciós naplóban (`code/transactionlog`) menti lemezre. A következő lépés az alkalmazás konténerizálása és deklaratív YAML manifestek segítségével történő telepítése Kubernetesbe.

## Konténerkép építése és a Vendoring (`go mod vendor`)

A többlépcsős (multi-stage) Dockerfile használatakor egy rejtélyes fordítási hibába ütközünk: a `podman image build` (vagy `minikube image build`) meghiúsul a `transactionlog replacement directory ../transactionlog does not exist` hibaüzenettel.

**A hiba oka:** Mivel a `transactionlog` csomagot nem publikáltuk a `pkg.go.dev`-re, a `go.mod` fájlban a `replace` direktívával a build könyvtáron kívül eső `../transactionlog` mappára hivatkoztunk, amelyhez a konténerépítő biztonsági okokból tiltja a hozzáférést.

**A megoldás (`go mod vendor`):** A Go beépített vendoring mechanizmusa a projekt gyökérkönyvtárán belüli `vendor/` mappába másolja az összes külső és helyi függőséget, így a build környezet teljesen önálló és reprodukálható lesz.

> **Biztonsági figyelmeztetés:** A `vendor/` mappába másolt csomagok nem frissülnek automatikusan mindaddig, amíg újra le nem futtatjuk a `go mod vendor` parancsot, így könnyen benne maradhatnak ismert biztonsági rések – ezért csak megfontoltan használjuk.

```dockerfile
# deploy/Dockerfile (többlépcsős build vendoring támogatással)
# 1. szakasz: Fordítás konténerizált Go környezetben
FROM docker.io/golang:latest as build
COPY . /leaderboard
WORKDIR /leaderboard
RUN CGO_ENABLED=0 GOOS=linux go build -a -o leaderboard

# 2. szakasz: Minimális futtató konténer
FROM scratch
COPY --from=build /leaderboard/leaderboard /
COPY static/index.html static/
CMD ["/leaderboard"]
```

```bash
# Függőségek bemásolása a vendor/ könyvtárba, majd az image megépítése:
go mod vendor
sudo podman image build -t localhost/leaderboard-trans -f deploy/Dockerfile .
```

## Deklaratív telepítés Kubernetesbe (YAML manifestek)

Összetettebb rendszereknél parancssori kapcsolók helyett deklaratív YAML manifest fájlokban írjuk le a kívánt Kubernetes erőforrásokat, majd a `kubectl apply -f <fájl>` paranccsal érvényesítjük őket.

- **Címkék és szelektorok (`labels` / `matchLabels`):** Kubernetesben szinte minden összerendelés címkék alapján működik – a Deployment a `selector.matchLabels` alapján azonosítja, mely Pod-ok tartoznak hozzá.
- **`imagePullPolicy: Never`:** Ez a beállítás jelzi a Kubernetesnek, hogy ne próbálja meg letölteni az image-et külső registryből, hanem a helyi gépen megépített `localhost/leaderboard-trans` képet használja.

```yaml
# deploy/kubernetes-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: leaderboard
  labels: { app: leaderboard }
spec:
  selector:
    matchLabels: { app: leaderboard }
  template:
    metadata:
      labels: { app: leaderboard }
    spec:
      containers:
      - name: leaderboard
        image: localhost/leaderboard-trans
        imagePullPolicy: Never
        ports:
        - containerPort: 8080
```

```bash
# Telepítés és külső elérés biztosítása (Minikube alatt: minikube tunnel):
kubectl apply -f deploy/kubernetes-deployment.yaml
kubectl expose deployment leaderboard --type=LoadBalancer --port 8080
export EXTERNAL_IP=$(kubectl get service leaderboard -o jsonpath="{.status.loadBalancer.ingress[0].ip}")
```

## Miért tűnik el mégis a ranglista újraindításkor?

Ha a fenti Deploymentbe feltöltünk egy pontszámot, majd végrehajtjuk a `kubectl rollout restart deployment leaderboard` parancsot, a `getScores` végpont ismét üres listát (`[]`) ad vissza.

**A jelenség oka:** A cloud-native alapelveknek megfelelően a Kubernetes Podok teljesen állapotmentesek, ezért a Pod helyi fájlrendszere is mulandó (ephemeral), akárcsak a memória – amint a Pod törlődik vagy újraindul, a lokális fájlrendszerén végzett összes módosítás (így a `/tmp/translog.log` is) megsemmisül.

## Állandó kötetek: PersistentVolume (PV) és PersistentVolumeClaim (PVC)

Ahhoz, hogy az adatok túléljék a Podok újraindítását, a Kubernetes PersistentVolume (PV) mechanizmusát kell használnunk, amely elvonatkoztatja a fizikai háttértárat (helyi lemez, hálózati tárhely vagy felhős tároló).

- **PersistentVolume (PV):** Magát a tárolókapacitást definiálja a klaszterben (a példában egy 5 MB-os `hostPath` típusú kötetet, amely a Kubernetes node helyi `/tmp` könyvtárát képezi le).
- **PersistentVolumeClaim (PVC):** Az alkalmazás igénybejelentése (igénylése) egy megfelelő méretű és hozzáférési módú (`ReadWriteOnce`) állandó kötetre.
- **A `hostPath` korlátja:** Mivel a `hostPath` a futtató node helyi fájlrendszerére támaszkodik, túléli ugyan a Pod újraindítását, de nem osztható meg több különböző node-on futó Pod között – több node-os megosztáshoz valódi hálózati tárolóra (például NFS-re) van szükség.

```yaml
# PV és PVC definíciója:
apiVersion: v1
kind: PersistentVolume
metadata:
  name: translog-volume
spec:
  capacity:
    storage: "5Mi"
  accessModes: [ ReadWriteOnce ]
  hostPath:
    path: "/tmp"
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: translog-claim
spec:
  accessModes: [ ReadWriteOnce ]
  resources:
    requests:
      storage: "5Mi"
```

A kötetet a Deployment YAML-ben két lépésben csatoljuk be: a `spec.template.spec.volumes` alatt hivatkozunk a `translog-claim` PVC-re, a konténer `volumeMounts` részében pedig megadjuk, hogy a Podon belül a `/tmp` útvonalra csatolja fel. Így a `kubectl rollout restart` után a Pod naplójából (`kubectl logs`) is látható, hogy az alkalmazás induláskor sikeresen visszaolvasta az eseményeket a tranzakciós naplóból.

# 2. Állapot kiszervezése (State Externalization)

## A horizontális skálázás problémája (2 Pod kísérlet)

A `hostPath` alapú kötet nem osztható meg több Pod között, ezért vizsgáljuk meg, mi történik, ha az eredeti memóriabeli Leaderboard alkalmazást horizontálisan skálázzuk több replikára:

```bash
kubectl scale deployment leaderboard --replicas=2
kubectl rollout restart deployment leaderboard
```

Ha ezután feltöltünk két pontszámot (`user1: 1`, `user2: 2`), majd többször egymás után lekérdezzük a `getScores` végpontot, teljesen véletlenszerű és inkonzisztens válaszokat kapunk (egyszer üres `[]` listát, máskor a pontszámokat).

**A hiba oka:** A Kubernetes LoadBalancer típusú Service minden bejövő HTTP kérést véletlenszerűen irányít valamelyik Podra (`leaderboard-1` vagy `leaderboard-2`). Mivel mindkét Pod a saját helyi memóriájában tárolja a ranglistát, az erőforrás-állapot széttöredezik (fragmented) a példányok között.

## A State Externalization fogalma

A perzisztencia önmagában csak a fél megoldás az immutability eléréséhez; a valódi állapotmentességhez az állapotot ki kell szervezni egy központi külső adatbázisba (**State externalization**), nem pedig az alkalmazás folyamatával együtt tárolni. A központi adattárnak két alapkövetelményt kell teljesítenie:

- **Konzisztencia (Consistency):** Minden alkalmazás-Pod ugyanazt az állapotváltozási sorrendet látja, és minden módosítás azonnal láthatóvá válik minden példány számára.
- **Perzisztencia (Persistence):** Az adatok túlélik a teljes rendszer újraindítását és az újbóli telepítéseket is.

**Képlet a skálázhatósághoz:**

$$
\text{Állapotmentesség (Statelessness)} = \text{Állapot kiszervezése} + \text{Perzisztencia}
$$

Ha ez teljesül, az alkalmazás szabadon skálázható horizontálisan anélkül, hogy a Podoknak egymással kellene szinkronizálniuk.

## A Redis kulcs-érték tár

A kiszervezéshez a Redis nyílt forráskódú, memóriabeli kulcs-érték adatbázist használjuk, amely biztonságosan kezeli a több száz Podtól érkező párhuzamos írási és olvasási kéréseket. A kulcsok minden esetben stringek, az értékek pedig többféle adatszerkezetet vehetnek fel (string, hash, lista, halmaz, rendezett halmaz), emellett a Redis támogatja a lemezes perzisztenciát, a pub/sub üzenetküldést, a tranzakciókat és a klaszterezést is.

## Szabványos Go modul könyvtárszerkezet és refaktorálás

Ahhoz, hogy az alkalmazásunk egyszerre támogassa a helyi memóriabeli tárolót (függőségmentes egységtesztekhez) és a Redis adatréteget (éles futtatáshoz), szabványos Go modul struktúrába rendezzük a kódot:

```text
leaderboard/
├── go.mod                        # Modul metaadatai
├── go.sum                        # Függőségek ellenőrzőösszegei
├── main.go                       # Belépési pont (több bináris esetén: cmd/exec1/main.go)
├── pkg/                          # KÜLSŐ modulok által is importálható csomagok
│   ├── api/
│   │   └── api.go                # Score struktúra és DataLayer interfész
│   └── db/
│       ├── local/                # Helyi memóriabeli implementáció + tesztek
│       │   ├── local_db.go
│       │   └── local_db_test.go
│       └── redis/                # Redis alapú implementáció
│           └── redis.go
├── internal/                     # CSAK ezen a modulon belül importálható csomagok
├── deploy/                       # Dockerfile és Kubernetes YAML manifestek
│   ├── Dockerfile
│   ├── kubernetes-local-db.yaml
│   └── kubernetes-redis-db.yaml
└── static/                       # Statikus webes erőforrások (más néven assets/)
    └── index.html
```

- **`pkg/` vs. `internal/`:** A `pkg/` alatti csomagokat más külső projektek is importálhatják (pl. `import "leaderboard/pkg/api"`), míg az `internal/` könyvtárba tett csomagok importálását maga a Go fordító tiltja meg bármely külső modul számára (ide kerülnek a belső segédfüggvények, alapértelmezett beállítások).
- **Körkörös importok tilalma (No circular dependencies):** Go-ban fordítási idejű hiba, ha két csomag kölcsönösen importálja egymást (`pkg1` ↔ `pkg2`). A csomagok függőségi gráfjának kötelezően irányított körmentes gráfnak (DAG) kell lennie.

## A Redis DataLayer implementálása Go-ban

A `go get github.com/go-redis/redis` csomag telepítése után a `redisDB` struktúrába beágyazzuk (struct embedding) a `*redis.Client` típust, így a kliens metódusai közvetlenül elérhetővé válnak. A kulcs-érték adatmodellben a játékos neve (`score.Name`) a kulcs, az aktuális pontszáma pedig a hozzá tartozó érték.

```go
package redis

import (
	"github.com/go-redis/redis"
	"leaderboard/pkg/api"
)

type redisDB struct {
	*redis.Client // Beágyazott Redis kliens
}

// NewDataLayer csatlakozik a Redis szerverhez és ellenőrzi a kapcsolatot.
func NewDataLayer(addr string) api.DataLayer {
	client := redis.NewClient(&redis.Options{
		Addr:     addr, // pl. "redis:6379"
		Password: "",
	})
	if _, err := client.Ping().Result(); err != nil {
		panic(err)
	}
	return &redisDB{Client: client}
}

// Add atomi módon növeli a játékos pontszámát a Redis IncrBy parancsával.
func (db *redisDB) Add(score api.Score) error {
	return db.IncrBy(score.Name, int64(score.Points)).Err()
}

// List végigiterál az összes kulcson a Scan iterátorral és összeállítja a listát.
func (db *redisDB) List() ([]api.Score, error) {
	ret := []api.Score{}
	iter := db.Scan(0, "*", 0).Iterator()
	for iter.Next() {
		key := iter.Val()
		val, err := db.Get(key).Int()
		if err != nil {
			return []api.Score{}, err
		}
		ret = append(ret, api.Score{Name: key, Points: val})
	}
	return ret, nil
}
```

Miután a `kubectl apply -f deploy/kubernetes-redis-db.yaml` paranccsal elindítjuk a Leaderboardot és a mögötte lévő Redis szervert, majd `kubectl scale deployment leaderboard --replicas=3` paranccsal 3 példányra skálázzuk, minden kérés konzisztens, naprakész ranglistát ad vissza.

# 3. Laza csatolás (Loose Coupling)

## Saját kulcs-érték tár építése: miért gond a naiv megközelítés?

Ha egy saját, minimalista kulcs-érték tárat építünk a Redis helyett, a naiv megoldás az lenne, hogy az adatréteg `Add` és `List` metódusait közvetlenül HTTP végpontokként (`/api/add`, `/api/list`) valósítjuk meg a tároló szerveren. Ha azonban később új funkcióra van szükségünk (például pontszám levonására vagy játékos törlésére), mind a Leaderboard alkalmazást, mind a kulcs-érték tárat módosítanunk és újra kell telepítenünk.

## Szoros csatolás (Tight Coupling) vs. Laza csatolás (Loose Coupling)

- **Szoros csatolás (Elosztott monolit):** A komponensek túl sokat tudnak egymás belső felépítéséről vagy fix hálózati címéről. Az egyik komponens módosítása kikényszeríti a másik átírását is – az ilyen rendszereket nevezzük **elosztott monolitnak** (distributed monolith).
- **Laza csatolás:** A komponenseket úgy tervezzük, hogy minimális közvetlen tudással rendelkezzenek egymásról, és absztrakt interfészeken, nyílt szabványos protokollokon (pl. HTTP / REST) keresztül kommunikáljanak. Így bármelyik szolgáltatás szabadon frissíthető, újratelepíthető vagy akár teljesen újraírható a függő rendszerek érintése nélkül.

## A laza csatolás 4 tipikus antimintája (Anti-patterns)

Ha az alábbi négy jelenség bármelyikét látjuk egy mikroszolgáltatás-architektúrában, az elosztott monolitra utal, ezért kerülni kell őket:

- **Törékeny adatcsere-protokollok (Fragile exchange protocols):** Olyan protokollok (pl. SOAP vagy CORBA), amelyek közvetlenül az alkalmazás belső adatszerkezeteiből generálják a kommunikációs szerződést; egy belső struktúra módosítása az összes szolgáltatást eltöri.
- **Megosztott függőségek (Shared dependencies):** Ha több szolgáltatás szorosan függ egy közös könyvtár adott verziójától, és a könyvtár frissítésekor az összes szolgáltatást egyszerre (in lockstep) kell frissíteni.
- **Közös időpillanathoz kötöttség (Shared point-in-time):** A szinkron kérés-válasz (request-response) kommunikáció feltételezi, hogy a hívott fél pontosan abban a pillanatban elérhető és azonnal válaszol – ez időbeli csatolást hoz létre.
- **Fix IP-címen futó szolgáltatások:** Ha a kliens beégetett IP-címen éri el a szervert (service discovery / DNS helyett), a szerver nem költöztethető el a kliens módosítása nélkül.

## Laza csatolású adatmodellek: SQL vs. NoSQL

A szoros csatolás elkerülése komoly adatmodellezési kihívás is:

- **Relációs adatbázisok (SQL):** Az alkalmazás belső állapotmodelljét merev SQL táblasémákba kényszerítik. Amikor az alkalmazás adatmodellje változik, az adatbázis sémáját is migrálni kell – ez szoros csatolást teremt az alkalmazás és az adatbázis között.
- **NoSQL kulcs-érték tárak (pl. Redis, MongoDB, Apache HBase):** Teljesen sémamentesek – tetszőleges értéket tárolnak string kulcsok alatt, így az alkalmazás változásakor nem kell módosítani az adatbázis struktúráját.
- **Kompromisszum:** Mivel nincs séma, az adatbázis nem tudja ellenőrizni a betöltött adatok típushelyességét és konzisztenciáját. **Ökölszabály:** Egyszerű, rugalmas API-khoz használjunk NoSQL-t, összetett, szigorúan strukturált adatokhoz pedig SQL-t.

## API-tervezési evolúció: a get-incr vs. a generikus get-set API

| Szempont | get-incr API (`map[string]int`) | Generikus get-set API (`map[string]string`) |
|---|---|---|
| **Műveletek** | `get(key string) int` és `incr(key string, inc int) int` | `get(key string) string` és `set(key, value string)` |
| **Adattípusok** | Merev (int-hez kötött); ha lebegőpontos (`float64`) pontok kellenek, a szervert is át kell írni. | Teljesen általános (minden adat ábrázolható stringként, pl. JSON-ként). |
| **Bővíthetőség** | Pontlevonáshoz vagy törléshez új API végpontokat kell fejleszteni a szerveren. | A komplex logika a kliensre kerül: növelés (`set(key, get(key)+x)`), kivonás (`set(key, get(key)-x)`), törlés szimulálása (`set(key, "")`). |
| **Újrapróbálhatóság** | **Nem újrapróbálható (not retriable):** ha egy `incr` kérés válasza elveszik a hálózaton, az újraküldés kétszer adja hozzá a pontot! | A `set` művelet **idempotens** (többszöri végrehajtása ugyanazt az állapotot eredményezi). |
| **Veszélyek** | Szerveroldali szoros csatolás. | A kliensoldali `get` + `set` lépések között versenyhelyzet (data race) léphet fel párhuzamos módosításoknál (ezt későbbi mintákkal kezeljük). |

# 4. Összegző tervezési receptek (Conclusions)

- **Kubernetes kötetek használata:** A PersistentVolume-ok (megfelelő hálózati meghajtóval, mint az NFS vagy S3, illetve StatefulSet-ekkel párosítva) képesek állapotot megőrizni és megosztani a Podok között, de az állapottartó komponensek futtatását Kubernetesben érdemes a minimálisra szorítani.
- **A cloud-native alaprecept:** Koncentráljuk az alkalmazás teljes állapotát egyetlen dedikált adatrétegbe, tegyük csak azt állapottartóvá (stateful), az összes többi mikroszolgáltatást pedig futtassuk teljesen állapotmentes (stateless) Podokban.
- **Generikus adatmodellek:** Tervezzünk általános adatmodelleket és API-kat, hogy megszüntessük az alkalmazás és az adattároló közötti szoros csatolást; a relációs (SQL) adatbázisokat pedig csak ott használjuk, ahol valóban indokoltak.
