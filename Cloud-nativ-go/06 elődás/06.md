# 1. Cloud Native tervezés és az elosztott rendszerek buktatói (Cloud Native Design)

## Monolit („Pets”) vs. Mikroszolgáltatások („Cattle”)

A hagyományos webalkalmazásokat „háziállatként” (Pets) kezelik: kézzel telepítik és konfigurálják őket fizikai szerverekre vagy virtuális gépekre, ami órákig tart, és meghibásodás esetén nehézkes a hibakeresés. Ezzel szemben a cloud-native rendszerekben „haszonállat” (Cattle) stílusú szolgáltatásokat építünk, amelyek az alábbi jellemzőkkel bírnak:

- Eldobható (throw-away) Linux konténerekben futnak a felhőben, és replikációval skálázódnak.
- Kis méretű, jól körülhatárolt üzleti feladatkörrel (bounded-context) rendelkező mikroszolgáltatásokból épülnek fel.
- Egymástól függetlenül telepíthetők (independently deployable), autonóm módon fejleszthetők és decentralizáltak.
- Szabványos hálózati protokollokon (például HTTP-n) keresztül kommunikálnak egymással.

## Az elosztott számítások 8 tévhite (The Fallacies of Distributed Computing)

Egy mikroszolgáltatás-alapú alkalmazásban egyetlen felhasználói kérés akár több tucat hálózati kommunikációs munkamenetet is elindíthat a szolgáltatások között – a cloud-native rendszerek tehát alapvetően elosztott rendszerek, amelyekben a hibák elkerülhetetlenek. L. Peter Deutsch (Sun Microsystems, 1991) fogalmazta meg azt a 8 klasszikus tévhitet, amelyeket a fejlesztők gyakran feltételeznek, de a valóságban soha nem igazak:

| Tévhit (Fallacy) | Mi a valóság elosztott rendszerekben? |
|---|---|
| 1. A hálózat megbízható | A kommunikáció megszakadhat, csomagok veszhetnek el, vagy félrekonfigurálhatják a hálózatot. |
| 2. A késleltetés (latency) nulla | Az adatok hálózaton történő mozgatása mérhető időt vesz igénybe. |
| 3. A sávszélesség végtelen | A hálózat egyszerre csak korlátozott mennyiségű adatot képes átvinni. |
| 4. A hálózat biztonságos | Nem az – minden érzékeny adatot titkosítani kell az átvitel során. |
| 5. A topológia nem változik | A szerverek és szolgáltatáspéldányok folyamatosan indulnak el és állnak le. |
| 6. Egyetlen adminisztrátor van | Több különböző üzemeltetői csapat dolgozik, gyakran eltérő (heterogén) megoldásokkal. |
| 7. Az adatátvitel költsége nulla | Az adatok szerializálása és hálózati mozgatása időbe és pénzbe kerül. |
| 8. A hálózat homogén | Minden hálózati környezet eltérő (gyakran drasztikusan különböző) tulajdonságokkal bír. |

## Cloud-native tervezési minták áttekintése

A fenti problémák kezelésére a cloud-native architektúra bevált tervezési mintákat (design patterns) kínál:

- **Megváltoztathatatlanság (Immutability):** Egyszerűvé teszi a „Cattle” stílusú szolgáltatások létrehozását, telepítését és üzemeltetését.
- **Laza csatolás (Loose coupling):** Állapotmentes, gyorsítótárazható (cacheable) és biztonságosan újrapróbálható (retriable) kommunikációs minták (pl. REST).
- **Rugalmasság / Hibatűrés (Resiliency):** A megbízhatatlan hálózatokból eredő hibák (csomagvesztés, késleltetés) kezelése.
- **Skálázhatóság (Scalability):** Egyszerű horizontális skálázás a változó terhelés kiszolgálására.
- **Menedzselhetőség és megfigyelhetőség (Manageability & Observability):** Az alkalmazás belső működésének irányítása és monitorozása.

> **Fontos tervezési alapelv:** Ezek a minták bevált gyakorlatok (best practices), nem pedig kötelező kőbe vésett szabályok. Alkalmazásuk megkönnyíti az életünket, de figyelmen kívül hagyásuk sem teszi lehetetlenné a fejlesztést – mindig az adott probléma sajátosságai alapján kell mérlegelni.

# 2. Megváltoztathatatlanság és Állapotmentesség (Immutability & Statelessness)

## A kísérlet: Mi történik a Leaderboarddal újraindításkor?

Ha elindítjuk az előző előadáson megírt Leaderboard alkalmazást egyetlen replikával Kubernetesben, feltöltünk néhány pontszámot, majd újraindítjuk a szolgáltatást, minden adatunk elvész:

```bash
# 1. Szolgáltatás indítása és publikálása Kubernetesben:
kubectl create deployment leaderboard --image=localhost/leaderboard
kubectl expose deployment leaderboard --type=LoadBalancer --port 8080
export EXTERNAL_IP=$(kubectl get service leaderboard -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
kubectl scale deployment leaderboard --replicas=1
kubectl rollout restart deployment leaderboard

# 2. Pontszámok feltöltése és lekérdezése:
curl -H "Content-Type: application/json" --request POST --data \
  '{"name":"user1","points":1}' http://${EXTERNAL_IP}:8080/api/addScore
curl -H "Content-Type: application/json" --request POST --data \
  '{"name":"user2","points":2}' http://${EXTERNAL_IP}:8080/api/addScore

curl http://${EXTERNAL_IP}:8080/api/getScores
# Kimenet: [{"name":"user2","points":2},{"name":"user1","points":1}]

# 3. Újraindítás szimulálása:
kubectl rollout restart deployment leaderboard
curl http://${EXTERNAL_IP}:8080/api/getScores
# Kimenet: []  <-- Minden adat elveszett!
```

## Miért történt ez, és miért kritikus a felhőben?

A Kubernetesben futó konténerek (Podok) a felhőben gyakran spontán leállnak vagy újraindulnak:

- Horizontális visszaskálázáskor (scale-in) a rendszer félig véletlenszerűen leállít podokat.
- Költséghatékonyság miatt gyakran használunk spot instance-okat (olyan virtuális gépeket, amelyeket a felhőszolgáltató bármikor visszavehet).
- Az alkalmazás hibára futhat vagy kifogyhat a memóriából (OOM).

Mivel a jelenlegi `localDB` a pontszámokat kizárólag a konténer operatív memóriájában (`scores []api.Score`) tárolja, a pod újraindításakor a teljes belső állapot végleg megsemmisül.

## Mutable vs. Immutable infrastruktúra

**Változékony (Mutable) alkalmazás:** Olyan szolgáltatás, amely a működése során beérkező API-kérések hatására megváltoztatja a saját belső állapotát (ilyen a memóriabeli Leaderboard). Ezek klasszikus „Pet” stílusú alkalmazások: ha egyetlen példányban él az adat, előbb-utóbb biztosan el fog veszni.

**Megváltoztathatatlan (Immutable) minta:** A szolgáltatásokat eldobható (ephemeral), állapotmentes (stateless) infrastruktúrára telepítjük, teljesen azonos konfigurációval, úgy, hogy maguk a futó példányok működés közben nem változtatják meg belső állapotukat.

**Előnyei:** Egyszerű telepítés (egyszer becsomagoljuk, és tetszőleges példányszámban elindítjuk) és adatbiztonság (az adat nem egyetlen törékeny konténer memóriájában él).

## Az állapotmentesség két fő eszköze

Ahhoz, hogy egy szolgáltatás immutable legyen, minden lényeges belső állapotát tudatosan kell kezelnünk. Ennek két fő eszköze van:

- **Perzisztencia (Persistence):** Az állapot túléli az őt létrehozó folyamat megszűnését; ehhez az adatokat nem felejtő háttértárra (lemezre/kötetre) kell írni (ez a jelen előadás témája).
- **Állapot kiszervezése (State externalization):** Az állapotot nem a feldolgozó folyamatban, hanem egy külső rendszerben (kulcs-érték tárban, központi adatbázisban, vagy magánál a kliensnél) tároljuk (ez a következő előadás témája).

> „A rossz programozók a kód miatt aggódnak. A jó programozók az adatszerkezetek és azok kapcsolatai miatt aggódnak.” – Linus Torvalds (a Linux megalkotója)

## Esettanulmány: Kliensoldali és szerveroldali állapot szétválasztása

Képzeljünk el egy képgaléria webalkalmazást, amely oldalanként 10 képet jelenít meg, és előre/hátra nyilakkal lehet lapozni benne. Kétféle állapotunk van:

- **Melyik kliens melyik oldalt nézi éppen:** Kliensenkénti állapot; elvesztése kellemetlen, de nem katasztrófa.
- **Maguk a képek:** Minden kliens számára közös adat; elvesztése katasztrófa.

**Naiv megoldás (Állapottartó szerver):** A szerver a memóriájában tárolja minden egyes kliens aktuális oldalszámát, és `getNextPage` / `getPrevPage` végpontokat kínál. Ez több százmillió felhasználónál nem skálázható, és szerver-újraindításkor elveszik a kliensek pozíciója.

**RESTful megoldás (Állapotmentes szerver):** A kliens aktuális oldalszámát áthelyezzük a kliens oldalra (például egy `current_page` JavaScript változóba), a szerver pedig egyetlen általános végpontot biztosít: `getPage?id=<oldalszám>`. A következő oldalhoz a kliens a `getPage?id=current_page+1`, az előzőhöz a `getPage?id=current_page-1` kérést hívja. A REST szakirodalomban ezt **hypermedia** megközelítésnek nevezik (az állapotot a kliensnek adott URL-ekbe kódoljuk), így a szerveroldali kérések teljesen állapotmentesek és biztonságosan újrapróbálhatók (retriable) lesznek.

## Resource State vs. Application State

| Jellemző | Resource State (Erőforrás-állapot) | Application State (Alkalmazás-állapot) |
|---|---|---|
| **Hol tároljuk?** | A szerveroldalon (perzisztens tárolóban). | A kliensoldalon (pl. böngészőben, cookie-kban, URL-ben). |
| **Kire vonatkozik?** | Általában minden kliens számára közös (pl. képek, ranglista). | Kliensenként egyedi kontextus (pl. melyik oldalon jár a felhasználó). |
| **Mennyire kritikus?** | Elvesztése kritikus, ezért biztonságosan perzisztálni kell. | Elvesztése nem kritikus, nem szükséges szerveroldalon tárolni. |

> (Megjegyzés: A két kategória nincs kőbe vésve – ha egy kliensspecifikus adat üzletileg kritikus, például egy webáruház kosarának tartalma, akkor azt átemeljük a szerverre, és onnantól resource state-ként kezeljük.)

# 3. Perzisztencia és a Tranzakciós Napló (Persistence & Transaction Log)

## Miért nem elég a rendszeres pillanatkép (Snapshot) mentés?

Kubernetesben a konténerekhez csatolhatunk tartós háttértárat (Pod → PersistentVolumeClaim (PVC) → PersistentVolume (PV)). Ha azonban az adatokat egyszerűen egy fájlba szeretnénk menteni, a naiv megoldás – például 5 másodpercenként kiírni a teljes memóriaállapotot (snapshot) egy fájlba – három súlyos hibával jár:

1. Nagy adatméret esetén feleslegesen sok CPU-időt emészt fel.
2. Két mentés között történő leálláskor elvesznek a legutóbbi módosítások.
3. Ha az alkalmazás éppen a fájl írása közben áll le, sérült, inkonzisztens állapotot kapunk.

## A tranzakciós napló (Transaction Log) elve

Az adatbázis-kezelő rendszerekből átvett megoldás az **append-only** (csak hozzáfűzhető) tranzakciós napló:

- Nem a teljes állapotot írjuk ki újra és újra, hanem minden állapotmódosító (mutating) műveletnél egyetlen új rekordot fűzünk a naplófájl végére.
- A Leaderboard esetében az `addScore` módosítja az állapotot (naplózzuk), míg a `getScores` csak lekérdezi azt (nem naplózzuk).
- Induláskor a szolgáltatás beolvassa és sorban újrajátssza (replay) a naplóban lévő eseményeket, így pontosan visszaállítja a legutolsó állapotot.
- Mivel elméletben a naplófájl a végtelenségig nőhet, éles rendszerekben időszakos pillanatképekkel (snapshots) kombinálják a méret kordában tartásához.

## A transactionlog modul és a fájlformátum

Létrehozzuk egy különálló `transactionlog` modult (`mkdir transactionlog && cd transactionlog && go mod init transactionlog`). Minden állapotmódosító eseményt egy `Event` struktúra ír le:

```go
package transactionlog

// Event egy a tranzakciós naplóba írt vagy onnan kiolvasott rekordot reprezentál.
type Event struct {
	Sequence uint64 // Egyedi, monoton növekvő sorszám (a napló érvényességének ellenőrzéséhez)
	Type     string // Az esemény típusa (pl. "addScore")
	Value    string // Az új érték JSON formátumú stringként kódolva
}
```

**Sororientált fájlformátum:** Minden sor egy eseményt tartalmaz, a mezőket tabulátor (`\t`) választja el egymástól:

```text
1	addScore	{"name":"x","points":2}
2	addScore	{"name":"user1","points":12}
```

**Írás és olvasás Go-ban:**

- Írás fájlba: `fmt.Fprintf(file, "%d\t%s\t%s\n", e.Sequence, e.Type, e.Value)`
- Beolvasás egy sorból: `err := fmt.Sscanf(line, "%d\t%s\t%s", &e.Sequence, &e.Type, &e.Value)`

## A TransactionLogger interfész és az aszinkron működés

Az interfész tervezésekor két eltérő használati módot kell kiszolgálnunk:

- **Aszinkron írás (`Write`):** A HTTP kéréskiszolgálónak nem szabad megvárnia a lassú lemezre írást. A `Write` csupán beteszi az eseményt egy csatornába és azonnal visszatér; a tényleges fájlba írást egy a `Run(ctx)` által indított háttér-goroutine végzi.
- **Hibacsatorna minta (Error channel pattern):** Mivel az írás aszinkron módon, külön goroutine-ban történik, a `Write` nem tud közvetlenül `error`-t visszaadni. Ezért a logger egy külön `chan error` csatornát tart fenn (amelyet az `Err()` metódus ad vissza), és ezen keresztül küldi ki az esetleges írási hibákat.
- **Szinkron helyreállítás (`ReadEvents`):** Induláskor a `ReadEvents()` szinkron módon visszaadja a naplóból kiolvasott `[]Event` szeletet, amelyet a program végigjár és visszajátszik az adatrétegbe.

```go
type TransactionLogger interface {
	Write(key, value string)
	Run(context.Context)
	ReadEvents() ([]Event, error)
	Err() chan error
}
```

## A FileTransactionLogger implementációja és tesztelése

A fájlalapú megvalósítás (`filelog.go`) az `os.OpenFile` függvénnyel nyitja meg a naplófájlt:

- `os.O_RDWR`: írásra és olvasásra is megnyitja a fájlt.
- `os.O_APPEND`: minden írást garantáltan a fájl végére fűz (nem írja felül a meglévő tartalmat).
- `os.O_CREATE`: létrehozza a fájlt, ha még nem létezik (a `0755` jogosultsági maszkkal).

```go
package transactionlog

import (
	"context"
	"fmt"
	"os"
)

type FileTransactionLogger struct {
	events       chan Event // Csatorna a bejövő események fogadására
	errors       chan error // Csatorna az aszinkron írási hibák jelentésére
	lastSequence uint64     // Az utoljára kiosztott sorszám
	file         *os.File   // A naplót tároló fájl leírója
}

// NewFileTransactionLogger létrehoz és megnyit egy fájlalapú tranzakciós naplót.
func NewFileTransactionLogger(fname string) (TransactionLogger, error) {
	file, err := os.OpenFile(fname, os.O_RDWR|os.O_APPEND|os.O_CREATE, 0755)
	if err != nil {
		return nil, err
	}
	return &FileTransactionLogger{file: file}, nil
}

// Run elindítja a háttér-goroutine-t, amely kiírja az eseményeket a fájlba.
func (l *FileTransactionLogger) Run(ctx context.Context) {
	l.events = make(chan Event, 16) // Pufferelt eseménycsatorna
	l.errors = make(chan error, 1)  // Pufferelt hibacsatorna

	go func() {
		defer close(l.events)
		defer close(l.errors)
		defer l.file.Close()

		for {
			select {
			case e := <-l.events:
				l.lastSequence++
				_, err := fmt.Fprintf(l.file, "%d\t%s\t%s\n", l.lastSequence, e.Type, e.Value)
				if err != nil {
					l.errors <- err
					return
				}
			case <-ctx.Done():
				// Ha a kontextust leállítják, a goroutine tisztán kilép
				return
			}
		}
	}()
}

// Write aszinkron módon elküldi az eseményt a naplózó csatornára.
func (l *FileTransactionLogger) Write(key, value string) {
	l.events <- Event{Type: key, Value: value}
}

func (l *FileTransactionLogger) Err() chan error {
	return l.errors
}
```

> (Megjegyzés a kódrészletekhez: Az előadás diáján érték-fogadó (`l FileTransactionLogger`) szerepel a metódusoknál, azonban a gyakorlatban pointer-fogadó (`l *FileTransactionLogger`) szükséges ahhoz, hogy a `Run` által létrehozott `l.events` csatornát a `Write` metódus is lássa. Emellett az előadás is megjegyzi, hogy ideális esetben a csatornát a küldő fél zárja le, de itt a `Run` csak a program leállásakor fejeződik be.)

## Egységteszt (`filelog_test.go`)

A teszt ellenőrzi, hogy az egyik logger példánnyal kiírt eseményt egy másik példány `ReadEvents()` metódusa képes-e visszaolvasni a fájlból:

```go
func TestFileTransactionLogger(t *testing.T) {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	logger1, _ := NewFileTransactionLogger(logFile)
	logger1.Run(ctx)
	logger1.Write("a", "1")

	logger2, _ := NewFileTransactionLogger(logFile)
	events, err := logger2.ReadEvents()
	if err != nil {
		t.Errorf("read-events: error %s", err.Error())
	}
	if len(events) != 1 {
		t.Errorf("wrong length")
	}
	if events[0].Type != "a" || events[0].Value != "1" {
		t.Errorf("unexpected event: %+v", events[0])
	}
}
```

## A main.go módosításai

- **Importálás és globális változók:** A csomagot a `translog` rövidítéssel importáljuk (`import translog "transactionlog"`), és globális változóban tároljuk a naplófájl elérési útját (`var logFile = "/tmp/translog.log"`) valamint a logger interfészt.
- **Visszaállítás induláskor (`initTransactionLog`):** A `main()` függvényben az adatréteg létrehozása után beolvassuk a korábbi eseményeket (`logger.ReadEvents()`), deszerializáljuk a JSON-t (`json.Unmarshal`), és visszajátsszuk őket a `db.Add(score)` hívással, majd elindítjuk a háttérfolyamatot (`logger.Run(context.Background())`).
- **Naplózás módosításkor (`handleAddScore`):** Miután a `db.Add(score)` sikeresen lefutott (`err == nil`), a `score` struktúrát JSON-ná alakítjuk (`json.Marshal`), és elküldjük a naplónak (`logger.Write("addScore", string(data))`).

```go
// Indítási folyamat a main()-ben:
db = NewDataLayer()
initTransactionLog()               // Korábbi események visszajátszása a fájlból
logger.Run(context.Background())   // Aszinkron naplózó goroutine indítása

// Módosítás a handleAddScore handlerben:
if err := db.Add(score); err == nil {
	data, _ := json.Marshal(score)
	logger.Write("addScore", string(data))
}
```

> (Megjegyzés: Az előadás 22. diáján lévő példakódban elírásként `if err := db.Add(score); err != nil` szerepel, de a logika szerint nyilvánvalóan sikeres adatbázis-művelet esetén, tehát `err == nil` ágon kell naplózni az eseményt.)
