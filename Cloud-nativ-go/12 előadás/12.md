# 1. Menedzselhetőség és deklaratív üzemeltetés (Manageability)

## A Manageability tervezési minta

A cloud-native alkalmazásokat működés közben is gyakran módosítani kell: új kódverziót kell telepíteni, konfigurációs paramétereket kell frissíteni, funkciókat (feature flags) kell ki- vagy bekapcsolni, megváltozhat egy függő mikroszolgáltatás IP-címe vagy domainneve, illetve rendszeresen cserélni (rotálni) kell a hitelesítő adatokat és TLS-tanúsítványokat. Ha ezekhez a műveletekhez újra kell írni a forráskódot vagy le kell állítani a teljes rendszert, az súlyosan rontja a rendelkezésre állást.

A **manageability** minta célja, hogy az alkalmazás viselkedése üzembe helyezéskor és futás közben is átfogóan módosítható legyen a forráskód megváltoztatása nélkül. A cloud-native menedzselhetőség négy fő területre épül:

- **Konfigurációkezelés:** A viselkedést meghatározó kulcsparaméterek külső módosítása (környezeti változókkal, parancssori argumentumokkal vagy konfigurációs fájlokkal – a klasszikus Unix démonok például a SIGHUP szignál hatására töltik újra élőben a konfigurációs fájljukat).
- **Monitorozás, naplózás és riasztás:** Visszajelzést adnak a menedzsment számára a rendszer és komponensei általános állapotáról.
- **Telepítő és frissítő eszközök:** Lehetővé teszik a komponensek egyszerű telepítését, frissítését, visszaállítását (rollback) és skálázását.
- **Szolgáltatásfelderítés (Service discovery) és leltár (Inventory):** Nyilvántartják az elosztott komponensek állapotát és elérhetőségét – Kubernetesben ezt a Service absztrakció (IP-cím vagy DNS-név alapú elérés), a `kubectl get endpoints` parancs (az egyes Podok IP-címeinek lekérdezése), valamint maguk a deklaratív YAML manifestek biztosítják.

## Imperatív vs. Deklaratív menedzsment és a Controller minta

A Kubernetes munkaterhelések két alapvetően eltérő szemléletben kezelhetők:

| Szempont | Imperatív menedzsment | Deklaratív / Idempotens menedzsment |
|---|---|---|
| **Működési elv** | Konkrét utasításokat adunk a rendszernek arról, hogy mit tegyen következő lépésként. | A rendszer kívánt végállapotát (desired state) írjuk le, és a platformra bízzuk az odavezető lépéseket. |
| **Tipikus parancs** | `kubectl create` / `scale` / `expose <erőforrás>` | `kubectl apply -f resource.yaml` |
| **Előnyök** | Gyors ad-hoc kipróbáláshoz egyszerű. | Megismételhető (idempotens), párhuzamosítható (a műveletek sorrendje nem számít), verziókezelhető és áttekinthető. |

A deklaratív működés motorját a Kubernetes **kontrollerek (Controllers)** és **operátorok (Operators)** adják. Minden kontroller egy adott erőforrástípust figyel (például a ReplicaSet kontroller a Deployment `spec.replicas` mezőjét), és változás esetén egy **egyeztető ciklusban (reconciliation loop)** addig hajt végre műveleteket, amíg a klaszter aktuális állapota meg nem egyezik a kívánt állapottal. Erre a deklaratív alapra épülnek a modern infrastruktúra-kezelő eszközök (Ansible, Terraform, Puppet, Chef), valamint a GitOps és az ArgoCD, ahol a Git tárolóba küldött egyetlen commit automatikusan érvényesíti a YAML manifesteket a klaszterben.

# 2. Go alkalmazások konfigurálása és Kubernetes integráció

## Konfigurációs irányelvek Go-ban

A Go alkalmazások konfigurálásához négy fő alapelvet érdemes követni:

1. **Konfiguráció leválasztása a kódról:** Ugyanazt a lefordított konténerképet különböző konfigurációkkal telepíthetjük a fejlesztői, teszt és éles környezetekbe.
2. **Deklaratív, verziókezelt konfiguráció:** Ne találjunk ki saját fájlformátumot – használjunk szabványos JSON, YAML vagy TOML formátumot.
3. **Hasznos Go kezdőértékek (Zero values):** Mivel a `bool` típus alapértelmezett zéró értéke `false`, úgy nevezzük el a kapcsolókat, hogy a `false` jelentse az alapértelmezett viselkedést (pl. alapból kikapcsolt funkciónál `enable_feature`, alapból bekapcsolt funkciónál pedig `disable_feature` legyen a flag neve).
4. **Egyértelmű precedencia-sorrend:** Nem ajánlott keverni a parancssori argumentumokat és a környezeti változókat, mert nehéz követni, melyik írja felül a másikat; komolyabb projektekhez a `spf13/viper` csomag használata javasolt, amely szabványos sorrendet követ: alapértelmezés → konfigurációs fájl → környezeti változók → külső konfigurációs forrás → parancssori flagek.

## Parancssori argumentumok (flag csomag) és környezeti változók (os.Getenv)

A korábbi előadáson a shardedkvstore shardok címeit közvetlenül beégettük a `main.go` forráskódjába (`kvstore-0.kvstore:8081,...`), ami sérti a menedzselhetőséget, mert minden shard-módosításhoz újra kellene építeni a konténerképet. A Go standard `flag` és `os` csomagjaival külsővé tehetjük az adatréteg módját (`mode`) és a shardok címlistáját (`addrs`):

```go
package main

import (
	"flag"
	"log"
	"os"
	"strings"

	"leaderboard/pkg/api"
	"leaderboard/pkg/db/kvstore"
	"leaderboard/pkg/db/local"
	"leaderboard/pkg/db/redis"
	"leaderboard/pkg/db/shardedkvstore"
)

func main() {
	// 1. Alapértelmezett értékek és parancssori flagek definiálása
	KVStoreMode := "local"
	KVStoreAddr := ""

	mode := flag.String("mode", KVStoreMode, "Data layer mode: local, redis, kvstore, or shardedkvstore")
	addrs := flag.String("addrs", KVStoreAddr, "Comma-separated list of address:port pairs")
	flag.Parse() // Automatikusan kezeli a -h / --help kapcsolót is

	// 2. Környezeti változók beolvasása (felülírják az alapértelmezést)
	if envMode := os.Getenv("KVSTORE_MODE"); envMode != "" {
		KVStoreMode = envMode
	}
	if envAddr := os.Getenv("KVSTORE_ADDR"); envAddr != "" {
		KVStoreAddr = envAddr
	}

	// 3. Parancssori flagek érvényesítése (felülírják a környezeti változókat)
	if mode != nil && *mode != "" {
		KVStoreMode = *mode // Pointer dereferálása!
	}
	if addrs != nil && *addrs != "" {
		KVStoreAddr = *addrs
	}

	// 4. Megfelelő DataLayer példányosítása az interfész mögött
	var db api.DataLayer
	switch KVStoreMode {
	case "local":
		db = local.NewDataLayer()
	case "redis":
		db = redis.NewDataLayer(KVStoreAddr)
	case "kvstore":
		db = kvstore.NewDataLayer(KVStoreAddr)
	case "shardedkvstore":
		shardList := strings.Split(KVStoreAddr, ",")
		log.Printf("Using sharded kvstore with %d shards", len(shardList))
		db = shardedkvstore.NewDataLayer(shardList)
	}
}
```

Kubernetesben parancssori argumentumokat a konténer sablon `command: ["/leaderboard"]` és `args: ["-mode", "shardedkvstore", "-addrs", "..."]` mezőivel adhatunk át (szavanként bontott listaként), de a Kubernetes ökoszisztémában a **környezeti változók használata az elsődleges**. (Megjegyzés: a 13. dián szereplő `command: "/leaderboard"` szintaxis helyett a Kubernetes YAML sémában lista formátumú `command: ["/leaderboard"]` szükséges.)

## ConfigMap, Secret és élő konfiguráció-frissítés Kubernetesben

A konfigurációs értékeket érdemes egy központi **ConfigMap** erőforrásba szervezni (érzékeny adatok, például jelszavak vagy TLS-kulcsok esetén pedig **Secret** erőforrásba, `secretRef` hivatkozással). A ConfigMap kétféleképpen csatolható be a Podba:

- **Környezeti változóként (`valueFrom.configMapKeyRef`):** Indításkor beolvassa az értékeket, de ha a ConfigMap később megváltozik, a futó Podok nem értesülnek róla – manuálisan újra kell indítani a Deploymentet (`kubectl rollout restart`). (Fontos: a `valueFrom` mechanizmus csak környezeti változóknál érhető el, parancssori `args` listánál nem.)
- **Kötetként becsatolva (`volumes` + `volumeMounts`):** Ha a ConfigMapet fájlokként csatoljuk fel a Pod fájlrendszerébe (pl. `/etc/config`), a Kubernetes a ConfigMap módosítása után automatikusan frissíti a fájlokat a futó konténerben is. Így az alkalmazás (pl. a `spf13/viper` fájlfigyelőjével) újraindítás nélkül, élőben át tudja állítani a viselkedését (például a naplózási szintet).

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: leaderboard-config
data:
  kvstoreMode: "shardedkvstore"
  kvstoreAddr: "kvstore-0.kvstore:8081,kvstore-1.kvstore:8081"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: leaderboard
spec:
  template:
    spec:
      containers:
      - name: leaderboard
        image: localhost/leaderboard:latest
        # 1. mód: Környezeti változók betöltése ConfigMapből
        env:
        - name: KVSTORE_MODE
          valueFrom:
            configMapKeyRef:
              name: leaderboard-config
              key: kvstoreMode
              optional: true # A Pod akkor is elindul, ha a kulcs hiányzik
        - name: KVSTORE_ADDR
          valueFrom:
            configMapKeyRef:
              name: leaderboard-config
              key: kvstoreAddr
              optional: true
        # 2. mód: ConfigMap becsatolása fájlokként élő frissítéshez
        volumeMounts:
        - name: config-volume
          mountPath: /etc/config
      volumes:
      - name: config-volume
        configMap:
          name: leaderboard-config
```

> **Üzemeltetési figyelmeztetések:** A konténer sablon (`spec.template.spec.containers`) vagy akár egyetlen Pod-címke (`label`) módosítása a Deployment azonnali újraindítását vonja maga után. Emellett a korábban tanult graceful shutdown hosszú türelmi ideje miatt a régi konfigurációval futó Podok sokáig életben maradhatnak – kritikus biztonsági frissítéseknél ezt érdemes figyelembe venni.

## Pod metaadatok injektálása (Downward API)

Ha az alkalmazásnak futás közben szüksége van a saját dinamikusan kiosztott IP-címére, a Pod nevére vagy a futtató node nevére, a Kubernetes `fieldRef` segítségével injektálhatja ezeket környezeti változókba:

```yaml
env:
- name: MY_NODE_NAME
  valueFrom: { fieldRef: { fieldPath: spec.nodeName } }
- name: MY_POD_NAME
  valueFrom: { fieldRef: { fieldPath: metadata.name } } # Go-ban os.Hostname()-ként is elérhető
- name: MY_POD_NAMESPACE
  valueFrom: { fieldRef: { fieldPath: metadata.namespace } }
- name: MY_POD_IP
  valueFrom: { fieldRef: { fieldPath: status.podIP } }
```

# 3. Megfigyelhetőség (Observability)

## Az Observability tervezési minta

A cloud-native rendszerek sok együttműködő mikroszolgáltatásból és összetett Kubernetes infrastruktúrából állnak. Az **observability** minta célja, hogy a rendszer belső állapotára a külső kimenetei alapján következtetni tudjunk anélkül, hogy új kódot kellene telepítenünk vagy újra kellene műszereznünk az alkalmazást. Míg a hagyományos monitorozás csak az előre ismert hibákra („known unknowns”) ad választ, a valódi megfigyelhetőség lehetővé teszi, hogy olyan váratlan problémákra („unknown unknowns”) is választ kapjunk, amelyekre a fejlesztéskor még nem is gondoltunk.

## A megfigyelhetőség 3 alappillére

- **Elosztott nyomkövetés (Distributed tracing):** Egyetlen felhasználói kérés útját követi végig a mikroszolgáltatások hálózatán keresztül, irányított körmentes gráfként (DAG) rekonstruálva a teljes folyamatot és feltárva a teljesítménybeli szűk keresztmetszeteket (egy service mesh, például az Istio, minimális kódmódosítással biztosítja).
- **Metrikák (Metrics):** A rendszer állapotát időben leíró numerikus adatpontok (samples), amelyeket idősoros adatbázisokban (pl. Prometheus, InfluxDB) tárolunk és Grafana segítségével vizualizálunk trendek és anomáliák felismeréséhez.
- **Naplók (Logs):** A rendszerben történt események megváltoztathatatlan (append-only), kontextusgazdag időrendi rögzítése; Kubernetesben a `kubectl logs <pod>` paranccsal élőben, a `kubectl logs <pod> --previous` kapcsolóval pedig egy összeomlott konténer utolsó üzeneteit (post-mortem elemzéshez) kérdezhetjük le.

## Metrikák: Push vs. Pull modell és a címkék veszélyei

Egy metrikaminta (sample) névből, numerikus értékből, ezredmásodperc pontosságú időbélyegből és kontextust adó címkékből (labels) áll (például `http_requests_total{service="addScore"} 17`). **Fontos tervezési szabály:** ne használjunk túl részletes vagy magas kardinalitású címkéket (például felhasználói azonosítókat), mert minden egyedi címkekombináció külön idősort (timeseries) hoz létre az adatbázisban.

A metrikagyűjtés két alapvető architektúrája:

- **Push-alapú gyűjtés (pl. Graphite, StatsD):** Maguk a Podok küldik el a metrikákat a központi gyűjtőnek – hátránya, hogy minden Podnak ismernie kell a gyűjtő címét.
- **Pull-alapú gyűjtés / Scraping (pl. Prometheus):** A Podok csak publikálnak egy `/metrics` HTTP végpontot, és a központi gyűjtő periodikusan lekérdezi (scrape) őket egy központilag karbantartott lista alapján.

## Strukturált naplózás és teljesítmény Go-ban

A túl bőbeszédű, strukturálatlan szöveges naplók megterhelik a Kubernetes naplógyűjtőjét és nehezen elemezhetők gépi eszközökkel. Éles rendszerekben dinamikusan állítható naplózási szinteket használunk (`DEBUG` hibakereséshez, `INFO` az alapműködéshez, `ERROR` csak a kritikus hibákhoz).

A standard `log` csomag helyett strukturált naplózást (`log/slog`, Logrus, Zap) érdemes használni, amely géppel könnyen feldolgozható JSON adatfolyamot állít elő:

```json
{"time":1604888110, "level":"info", "method":"GET", "path":"/help", "duration":23, "message":"Access"}
```

A strukturált könyvtárak nemcsak jobban kereshetők, hanem nagyságrendekkel gyorsabbak is: a hagyományos `log.Printf("Event: %s", formatComplexEvent())` akkor is kiértékeli a drága formázó függvényeket, ha a naplózási szint miatt az üzenetet végül ki sem írja, míg a strukturált kulcs-érték címkék minimális memóriafoglalással dolgoznak:

| Go naplózó csomag | Műveleti idő (ns/op) | Relatív lassulás a Zap-hez képest | Memóriafoglalás (allocs/op) |
|---|---|---|---|
| **Zap** | 118 ns/op | +0% | 0 allocs/op |
| **Zap (sugared)** | 191 ns/op | +62% | 2 allocs/op |
| **Standard library (log)** | 499 ns/op | +323% | 2 allocs/op |

# 4. Összegző tervezési tanulságok

- **Menedzselhetőség a felhőben:** Mivel a felhőben az alkalmazásunk távoli szervereken („someone else's computer”) fut, a viselkedését újrafordítás nélkül kell tudnunk módosítani környezeti változókkal, parancssori kapcsolókkal és Kubernetes ConfigMap/Secret erőforrásokkal – újraindítás nélküli módosításokhoz pedig becsatolt konfigurációs fájlok figyelésével.
- **Teljes körű rálátás a rendszerre:** A strukturált naplózás, az elosztott nyomkövetés és a pull-alapú metrikagyűjtés együtt teszi lehetővé a biztonsági incidensek, a teljesítménybeli szűk keresztmetszetek és a hibás komponensek gyors azonosítását.
