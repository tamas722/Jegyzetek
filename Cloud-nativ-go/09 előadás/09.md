# 1. Hibatípusok és a hibatűrés (Resilience) alapjai

## Hol tartunk most? A mikroszolgáltatás-architektúra sérülékenysége

A Leaderboard alkalmazásunk jelenleg két különálló mikroszolgáltatásból áll: egy állapotmentes webszerverből (amely kiszolgálja a statikus HTML/JS felületet, valamint a `getScores` és `addScore` végpontokat) és a háttérben futó kvstore adatrétegből (amely a `get`, `put`, `list` API-t nyújtja, és tranzakciós naplóba menti az állapotot). Mivel minden felhasználói kérés kiszolgálásához a webszervernek hálózaton keresztül kell kommunikálnia a kvstore-ral, a rendszer működőképessége kritikusan függ a hálózati hibák kezelésétől és a műveletek újrapróbálhatóságától (retriability).

## Kísérletek hibainjektálással (Istio Service Mesh)

Az Istio service mesh hibainjektáló (fault injection) funkciójával valósághűen szimulálhatjuk a hálózati anomáliákat anélkül, hogy módosítanánk az alkalmazás kódját:

- **Késleltetés injektálása (Timeout kísérlet):**
  Ha az Istio segítségével 7 másodperces fix késleltetést (`fixedDelay: 7s`) injektálunk a kvstore felé menő minden hívásba, a `getScores` kérés ugyan lefut, de minden válasz 7 másodpercet késik. Azok a kliensek, amelyek rövidebb időkorláttal dolgoznak (pl. `curl --max-time 2`), válasz nélkül hibával leállnak (`Operation timed out after 2000 milliseconds`). A valóságban a hibák ráadásul véletlenszerűen jelentkeznek (pl. `percentage: { value: 33.3 }` esetén minden harmadik kérés lassul be).
- **HTTP 500 hiba injektálása (Fail kísérlet):**
  Ha csak a kvstore `/api/put` végpontjára érkező hívásokat szakítjuk meg HTTP 500 Internal Server Error válasszal (miközben a `get` és a `list` hibátlanul működik), a Leaderboard teljesen működésképtelenné válik, és az `addScore` kérések örökre beragadnak. Ennek oka, hogy az adatréteg egy végtelen `for` ciklusban próbálja újraküldeni a sikertelen `put` kérést, így végtelen újrapróbálkozó hurokba (infinite retry loop) kerül.

```yaml
# Istio VirtualService példa HTTP 500 hiba injektálására a /api/put végpontra:
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: kvstore-500
spec:
  hosts: [ kvstore ]
  http:
  - match:
    - uri: { exact: "/api/put" }
    fault:
      abort:
        httpStatus: 500
        percentage: { value: 100 }
    route:
    - destination: { host: kvstore }
  - route:
    - destination: { host: kvstore }
```

## Hibatípusok elosztott rendszerekben

Ahogy az elosztott rendszerek mérete és összetettsége nő, a hibák elkerülhetetlenné válnak, és gyakran dominóhatásként (cascading errors) terjednek végig az alrendszereken, amíg az egész rendszer össze nem omlik:

- **Teljes leállás (Failure):** Egy alrendszer teljesen megszűnik válaszolni a beérkező kérésekre.
- **Szürke hiba (Grey failure):** Súlyos teljesítményromlás, véletlenszerű csomagvesztés, akadozó I/O műveletek, memóriavergődés (memory thrashing), kapacitáshiány vagy nem végzetes kivételek.
- **Heisenbug:** Olyan szoftverhiba, amely látszólag véletlenszerűen eltűnik vagy megváltoztatja a viselkedését, különösen akkor, ha megpróbáljuk megfigyelni vagy hibakeresővel vizsgálni.

## A reziliencia (Resiliency) tervezési minták rendszerezése

A cloud-native tervezés a **design for failure** elvet követi: a rendszerbe beépített automatizmusok gondoskodnak arról, hogy egy alrendszer hibája esetén is működőképes maradjon (szükség esetén csökkentett funkcionalitással). A mintákat három feladatkör és két oldal (kliens- és szerveroldal) szerint csoportosítjuk:

| Feladatkör | Kliensoldali minták (Client-side) | Szerveroldali minták (Server-side) |
|---|---|---|
| **Hibaészlelés (Failure detection)** | Állapotellenőrzések (Health checks) | Állapotellenőrzések (Health checks) |
| **Hibakezelés (Failure mitigation)** | Időkorlát (Timeout), Újrapróbálkozás (Retry), Áramkör-megszakító (Circuit-breaking) | Redundancia (Redundancy), Kecses leállás (Graceful shutdown) |
| **Túlterhelés-megelőzés (Overload prevention)** | Sebességkorlátozás (Rate-limit), Pergésmentesítés (Debounce) | Sebességkorlátozás (Rate-limit), Terheléseldobás (Load-shedding) |

> (Megjegyzés: Az előadáson bemutatott mintakódok az átláthatóság kedvéért nem szálbiztosak, ezért éles környezetben több goroutine-ból való párhuzamos használathoz szinkronizációra van szükség.)

# 2. Kliensoldali hibakezelési minták (Client-side Failure Mitigation)

## 1. Timeout minta (Időkorlát)

A timeout a kliens első védelmi vonala a hibásan vagy túl lassan működő szerverekkel szemben: ha egy hívás a vártnál tovább tart, a kliens nem vár tovább a végtelenségig, hanem hibával megszakítja a várakozást. Ez hibaelhatárolást (fault isolation) biztosít és megakadályozza a kaszkádolt összeomlásokat.

Go nyelven az általános végrehajtható feladatokat egy egyszerű lezárás (closure) típussal írjuk le (`type Closure func() error`), míg a megszakítható feladatok egy `context.Context` paramétert is kapnak (`type ClosureContext func(context.Context) error`). A `WithTimeout` dekorátor függvény egy hagyományos `Closure`-t alakít át `ClosureContext`-té:

```go
type Closure func() error
type ClosureContext func(context.Context) error

// WithTimeout időkorláttal ruház fel egy hagyományos Closure függvényt.
func WithTimeout(f Closure) ClosureContext {
	return func(ctx context.Context) error {
		cherr := make(chan error, 1) // Pufferelt csatorna, hogy a goroutine ne ragadjon be
		go func() {
			cherr <- f()
		}()

		select {
		case err := <-cherr:
			return err // A függvény időben lefutott
		case <-ctx.Done():
			return ctx.Err() // Lejárt az időkorlát ("context deadline exceeded")
		}
	}
}
```

> (Megjegyzés: A dián pufferolatlan `make(chan error)` és `defer close(cherr)` szerepel, azonban ha a `ctx.Done()` ág fut le előbb, a háttér-goroutine később egy lezárt csatornába próbálna írni, ami pánikot okozna – éles kódban ezért az 1 elemű pufferelt csatorna biztonságosabb.)

**Veszély – Zombi goroutine-ok (Zombie goroutines):** Ha egy 40 másodpercig alvó függvényt (`time.Sleep(40 * time.Second)`) 1 másodperces timeouttal hívunk meg, a `WithTimeout` ugyan 1 másodperc után visszatér hibával, de a `runtime.NumGoroutine()` értéke 2 lesz (a főszál mellett a háttérben még 39 másodpercig fut az elindított goroutine). **Alapszabály:** Go-ban soha ne indíts olyan goroutine-t, amelyet nem tudsz leállítani – a gyakorlatban mindig a `context.Context`-et közvetlenül elfogadó `ClosureContext` mintát használd!

## 2. Retry minta és Backoff stratégiák (Újrapróbálkozás)

Ha egy hálózati kérés meghiúsul, feltételezhetjük, hogy átmeneti hibáról (transient fault) van szó, és újrapróbálhatjuk a hívást – kizárólag akkor, ha az adott API újrapróbálható (retriable), például idempotens.

A naiv, késleltetés nélküli végtelen újrapróbálkozás (tight loop) ún. **újrapróbálkozási vihart (retry storm)** okoz, amely másodpercenként több ezer kéréssel teljesen elárasztja és végleg térdre kényszeríti a még működő szervereket is. Ennek elkerülésére visszalépési (backoff) stratégiákat alkalmazunk:

| Stratégia | Működési elv | Előnyök és hátrányok |
|---|---|---|
| **Fix várakozás (Fixed-duration)** | Minden sikertelen próba után állandó ideig (pl. 2s) várakozik. | Egyszerű, de sok kliens esetén nem skálázódik jól. |
| **Exponenciális visszalépés (Exponential backoff)** | A várakozási idő minden próbálkozással megduplázódik (`backoff <<= 1`) egy felső korlátig (Cap). | Csökkenti a terhelést, de ha 1000 kliens egyszerre kap hibát, egyszerre is fognak újrapróbálkozni (clustered retries tüskék). |
| **Véletlenített exponenciális (Random exponential backoff)** | Az exponenciálisan növekvő várakozási időhöz véletlenszerű eltolást (jitter) ad hozzá. | Időben egyenletesen szétteríti a kliensek újrapróbálkozásait, teljesen megelőzve a retry storm-ot. |

```go
type Backoff struct {
	Base      time.Duration // Kezdeti várakozási idő
	Cap       time.Duration // Maximális várakozási idő két próba között
	Jitter    float64       // Véletlen szórás tényezője
	NumTrials int           // Összes próbálkozás maximális száma
}

// WithRetry véletlenített exponenciális visszalépéssel próbálja újra a Closure hívását.
func WithRetry(f Closure, wait Backoff) Closure {
	return func() error {
		err := f()
		base, cap := wait.Base, wait.Cap

		for backoff, step := base, wait.NumTrials-1; err != nil && step > 0; backoff, step = backoff<<1, step-1 {
			if backoff > cap {
				backoff = cap
			}
			jitter := rand.Float64() * float64(backoff) * wait.Jitter
			sleep := base + time.Duration(jitter)
			time.Sleep(sleep)
			err = f()
		}
		return err
	}
}

// A dekorátorok szabadon egymásba ágyazhatók (pl. Retry + Timeout):
func WithTimeoutRetry(f Closure, wait Backoff) ClosureContext {
	return WithTimeout(WithRetry(f, wait))
}
```

> (Megjegyzés a kódhoz: a 24. dián `sleep := base + time.Duration(jitter)` szerepel, míg a klasszikus exponenciális növekedésnél az aktuális `backoff` értékéhez szokás hozzáadni a jittert.)

## 3. Circuit Breaker minta (Áramkör-megszakító)

Ha egy szerver tartósan leállt, a további újrapróbálkozások csak feleslegesen terhelik a hálózatot és várakoztatják a hívó felet. Az áramkör-megszakító (circuit breaker) minta megvédi a rendszert az ilyen felesleges köröktől (**Fail Fast**):

- **Zárt állapot (Closed):** Normál működés; a kérések átmennek a szerver felé. Ha egymás után `FailureThreshold` alkalommal hibát kapunk, az áramkör kinyit.
- **Nyitott állapot (Opened):** A hívások el sem indulnak a hálózaton, a függvény azonnal hibával (`"service unreachable"`) tér vissza.
- **Automatikus visszazárás:** A `CloseInterval` időtartam eltelte után az áramkör spontán visszazár (`stateClosed`), hogy ellenőrizze, helyreállt-e a szerver.

```go
type Breaker struct {
	FailureThreshold int           // Ennyi egymást követő hiba után nyit az áramkör
	CloseInterval    time.Duration // Ennyi idő után zár vissza spontán
}

type breakerState int

const (
	stateOpened breakerState = iota
	stateClosed
)

func WithCircuitBreaker(f Closure, breaker Breaker) Closure {
	consecutiveFailures := 0
	lastAttempt := time.Now()
	state := stateClosed

	return func() error {
		// Ha nyitva van, de eltelt a CloseInterval, próbáljuk meg visszazárni
		if state == stateOpened && time.Since(lastAttempt) > breaker.CloseInterval {
			state = stateClosed
			consecutiveFailures = 0
		}
		if state == stateOpened {
			return errors.New("service unreachable") // Fail Fast
		}

		lastAttempt = time.Now()
		err := f()
		if err != nil {
			consecutiveFailures++
			if consecutiveFailures >= breaker.FailureThreshold {
				state = stateOpened
			}
		} else {
			consecutiveFailures = 0
		}
		return err
	}
}
```

# 3. Kliensoldali túlterhelés-megelőzés (Client-side Overload Prevention)

## 1. Debounce minta (Pergésmentesítés)

Még a hibátlanul működő hívások is túlterhelhetik a hálózatot, ha egy rövid időablakban hirtelen nagyon sokszor (burst) futnak le (például amikor egy felhasználó gyorsan gépel egy keresőmezőbe, amely minden leütésre automatikus kiegészítést kér a szervertől). A debounce egy adott időintervallumon belül korlátozza a hívások számát, és két fő stratégiája létezik:

- **Function-first:** Az első hívás azonnal lefut és elindít egy `d` időtartamú időzítőt; az időzítő lejártáig minden további hívást elnyom (és a gyorsítótárazott hibát adja vissza). Mikroszolgáltatások közötti gyakori hívások ritkítására használják.
- **Function-last:** Megvárja, amíg a hívássorozat után legalább `d` ideig csend van (nem érkezik újabb hívás), és csak ezután hajtja végre a belső függvényt – ez ideális a szövegmezős automatikus kiegészítéshez.

```go
func WithDebounceFirst(f Closure, d time.Duration) Closure {
	var threshold time.Time
	var err error

	return func() error {
		if time.Now().Before(threshold) {
			return err // Az időablakon belül vagyunk: nem hívjuk meg újra f()-et
		}
		err = f()
		threshold = time.Now().Add(d)
		return err
	}
}
```

## 2. Rate-limiter minta (Sebességkorlátozás)

A rate-limiter a szerverhívások maximális frekvenciáját korlátozza időegységenként (például egy felhasználó legfeljebb 10 kérést indíthat másodpercenként). Míg a debounce az összetorlódott híváshullámokra (burst) fókuszál (hogy egy hullámon belül csak egyszer fusson le a hívás), addig a rate-limiter egyenletes felső korlátot szab a forgalomnak.

**Token bucket (Zsetonvödör) algoritmus:** A leggyakoribb megvalósításban egy „vödör” legfeljebb $N$ darab zsetont képes tárolni. Minden hívás kivesz egy zsetont a vödörből (ha a vödör üres, a hívást elutasítja), a rendszer pedig állandó ütemben tölti vissza a zsetonokat a vödörbe.

# 4. Esettanulmány: Hibatűrő Leaderboard és tervezési tanulságok

## A resilientkvstore adatréteg megvalósítása

Összegyűjtjük a fenti mintákat a `code/resilient` csomagba, bekötjük a Leaderboard projektbe (`go mod edit -replace resilient=../resilient && go mod tidy && go mod vendor`), és létrehozzuk a `pkg/db/resilientkvstore` adatréteget.

A korábbi végtelen `for` ciklus helyett az `Add` metódusban a `get` + pontszámnövelés + `put` műveletsort egy `Closure`-be csomagoljuk, és átadjuk a `resilient.WithRetry` dekorátornak (a `resilient.DefaultBackoff` alapértelmezés szerint legfeljebb 4 újrapróbálkozást végez véletlenített exponenciális visszalépéssel):

```go
func (db *kvstore) Add(score api.Score) error {
	retrier := resilient.WithRetry(func() error {
		// 1. Jelenlegi pontszám és verzió lekérdezése
		r, err := http.Get(db.url + "/api/get?id=" + score.Name)
		if err != nil || r.StatusCode != http.StatusOK {
			return errors.New("get failed")
		}
		vValue := /* HTTP válasz JSON deszerializálása */
		vValue.Value += score.Points

		// 2. Frissített pontszám mentése verzióellenőrzéssel
		r, err = http.Post(db.url+"/api/put", "application/json", /* vValue JSON */)
		if err != nil || r.StatusCode != http.StatusOK {
			return errors.New("put failed") // Hiba esetén azonnal visszatérünk, a retrier kezeli a várakozást!
		}
		return nil
	}, resilient.DefaultBackoff)

	return retrier()
}
```

## Tesztelés hibainjektálással és a Chaos Testing szemlélet

Ha a `main.go`-t átállítjuk a `resilientkvstore.NewDataLayer("kvstore:8081")` használatára, majd az Istio segítségével 50%-os valószínűségű HTTP 500 hibát injektálunk a `/api/put` végpontra (vagy a kvstore-t `KVSTORE_FAULT_INJECTION=1` módban indítva a `/api/fault` végponton állítunk be hibákat), az `addScore` kérések a háttérben történő elutasítások ellenére 1–5 másodpercen belül sikeresen lefutnak.

A kliensoldali reziliencia-minták tudatos alkalmazása lehetővé teszi, hogy a mikroszolgáltatások kontrollált módon, a teljes rendszer összeomlása nélkül vészeljék át a függőségeik hibáit. Ez a megközelítés annyira megbízhatóvá teszi a rendszereket, hogy számos modern cloud-native szolgáltatást már éles környezetben is szándékos véletlenszerű hibainjektálással tesztelnek (**chaos testing**).
