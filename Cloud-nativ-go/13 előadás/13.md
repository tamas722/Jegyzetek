# 1. A Service Mesh architektúra és motivációja

## Miért nem elegendőek a kliensoldali programkönyvtárak?

A cloud-native tervezés öt alappillérének (skálázhatóság, laza csatolás, hibatűrés, menedzselhetőség, megfigyelhetőség) megvalósításához a nagy technológiai vállalatok kezdetben saját programkönyvtárakat fejlesztettek (például a Google a Stubby-t, a Netflix a Hystrix-ot, a Twitter pedig a Finagle-t, hasonlóan a korábban írt Go `resilient` modulunkhoz vagy a Dapr futtatókörnyezethez). A mikroszolgáltatás-architektúrák növekedésével azonban két súlyos korlát jelentkezett:

- **Többnyelvű (polyglot) környezetek:** Ha az egyik szolgáltatás Go-ban, a másik Pythonban vagy Javában íródik, minden egyes programozási nyelvhez külön implementálni és karbantartani kell ugyanazokat a hibatűrési és megfigyelhetőségi könyvtárakat.
- **Központi vezérlés hiánya:** Ha a próbálkozások számát vagy az időkorlátokat a forráskódban rögzítjük (pl. `NumTrials: 3`, `Base: 100 * time.Millisecond`), akkor egy paraméter módosításához, vagy egy retry storm alatti vészleállításhoz újra kell fordítani és telepíteni az egész alkalmazást.

## A Service Mesh minta és a Sidecar Proxy felépítés

A **service mesh** minta a hibatűrési, forgalomirányítási, biztonsági és megfigyelhetőségi funkciókat kiemeli az alkalmazáskódból, és egy dedikált, platformszintű infrastruktúrarétegként helyezi a Kubernetes fölé.

A működés alapja a **sidecar proxy architektúra**, amely két síkra oszlik:

- **Adatsík (Data plane):** Minden alkalmazáskonténer mellé, ugyanabba a Podba egy programozható HTTP proxy konténer (pl. Envoy az Istio esetében) kerül, amely transzparensen elfogja a Pod összes be- és kimenő hálózati forgalmát, és kikényszeríti a szabályokat anélkül, hogy az alkalmazás tudna róla.
- **Vezérlősík (Control plane, pl. `istiod`):** Az üzemeltetők deklaratív Kubernetes YAML manifestekben adják meg a házirendeket, a vezérlősík pedig dinamikusan letölti a konfigurációt, a szolgáltatásfelderítési adatokat és a tanúsítványokat az összes sidecar proxyba.

# 2. Forgalomirányítás, biztonság és megfigyelhetőség Istio-val

## Forgalomirányítás és hibatűrési házirendek (VirtualService, Gateway API)

Az Istio (hasonlóan a Linkerd vagy Kong megoldásokhoz) deklaratív erőforrásokkal teszi lehetővé a hálózati viselkedés futásidejű szabályozását:

- **Hibatűrési szabályok (VirtualService):** Az alkalmazáskód módosítása nélkül állíthatunk be globális időkorlátot és automatikus újrapróbálkozást egy célzott szolgáltatás (pl. kvstore) minden HTTP hívására.
- **Külső forgalom szűrése (Gateway és HTTPRoute):** A Kubernetes Gateway API segítségével külső terheléselosztót hozhatunk létre a 80-as porton, és szigorúan korlátozhatjuk, hogy kívülről kizárólag a támogatott végpontok (`/`, `/api/getScores`, `/api/addScore`) legyenek elérhetők.

```yaml
# 1. Hibatűrési házirend a kvstore hívásokhoz (VirtualService)
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: kvstore
spec:
  hosts: [ "kvstore" ]
  http:
  - route: [ { destination: { host: kvstore } } ]
    timeout: 5s
    retries:
      attempts: 3
      perTryTimeout: 200ms
---
# 2. Külső hozzáférés korlátozása csak a publikus végpontokra (Gateway API)
apiVersion: gateway.networking.k8s.io/v1beta1
kind: Gateway
metadata:
  name: gateway
spec:
  gatewayClassName: istio
  listeners: [ { name: default, port: 80, protocol: HTTP } ]
---
apiVersion: gateway.networking.k8s.io/v1beta1
kind: HTTPRoute
metadata:
  name: leaderboard
spec:
  parentRefs: [ { name: gateway } ]
  hostnames: [ "leaderboard" ]
  rules:
  - matches:
    - path: { value: "/" }
    - path: { value: "/api/getScores" }
    - path: { value: "/api/addScore" }
    backendRefs: [ { name: leaderboard, port: 8080 } ]
```

> (Megjegyzés: A 8. dia szöveges magyarázatában 500 ms-os globális timeout szerepel, míg a példaként megadott YAML-ben `timeout: 5s` látható.)

## Biztonság: L7 hozzáférés-vezérlés és kölcsönös TLS (mTLS)

Mivel a sidecar proxyk egészen az alkalmazási (HTTP) rétegig feldolgozzák a forgalmat, két szinten is megerősíthetjük a klaszter biztonságát:

- **Alkalmazásrétegbeli tűzfal (Default-deny):** A VirtualService segítségével előírhatjuk, hogy a `kvstore.default.svc.cluster.local` szolgáltatás felé kizárólag a `/api/get`, `/api/put` és `/api/list` útvonalakra érkező GET vagy POST kérések haladhassanak át, minden más hívás blokkolásra kerül.
- **Kölcsönös TLS titkosítás (PeerAuthentication):** Alapértelmezés szerint a Podok közötti HTTP forgalom titkosítatlan. Egyetlen PeerAuthentication manifest alkalmazásával (`mode: STRICT`) az Istio automatikusan HTTPS-re emeli a kommunikációt a sidecar proxyk között, kiosztja és rotálja a TLS tanúsítványokat, valamint kölcsönösen hitelesíti a kliens és szerver oldalt, megakadályozva a szolgáltatások megszemélyesítését.

```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
spec:
  mtls:
    mode: STRICT
```

## Megfigyelhetőség: Kiali, hibainjektálás és elosztott nyomkövetés

Mivel minden forgalom áthalad a sidecar proxykon, a Prometheus közvetlenül ezekből gyűjti a metrikákat, amelyeket a **Kiali** grafikus konzolon valós időben elemezhetünk (szolgáltatásgráf, kérések/mp, HTTP státuszkódok, válaszidők és riasztások).

**Esettanulmány a Kiali segítségével:** Ha hibainjektálással a `/api/list` kérések 10%-át HTTP 500 hibával elutasítjuk, a Kiali azonnal megmutatja, hogy a hibák továbbgyűrűznek a felhasználók felé (~9%-os hibaarány a leaderboard kimenetén), mert a `resilientkvstore` `List()` metódusából kimaradt a `WithRetry` dekorátor. A `WithRetry` pótlása után a sikerességi arány 100%-ra ugrik, ugyanakkor a Kiali grafikonján a 95. percentilis késleltetés (p95) ~500 ms-ra nő (miközben az átlagos késleltetés alacsony marad), ami pontosan tükrözi az újrapróbálkozások 250 ms-os visszalépési idejét.

**Elosztott nyomkövetés (Distributed tracing):** Az OpenTelemetry és a Jaeger segítségével kérésenként rekonstruálhatjuk a hívási láncot és az egyes komponensekben töltött időt. Ehhez az alkalmazásnak mindössze annyit kell tennie, hogy a bejövő HTTP kérésből kiolvassa a sidecar által generált `x-request-id` fejlécet, és továbbítja a lefelé (downstream) indított HTTP kérésekben.

# 3. A Twelve-Factor App módszertan

Ahogy a cloud-native rendszerek tervezési mintái összeállnak, egy egységes fejlesztési és üzemeltetési módszertan rajzolódik ki, amelyet a **Twelve-Factor App** (12factor.net) 12 alapelve foglal össze:

| # | Alapelv | Lényeg és cloud-native / Kubernetes megvalósítás |
|---|---|---|
| **I.** | **Codebase** | Egyetlen verziókezelt kódbázis (Git), amelyből több telepítés (deploy – pl. staging, prod) készül; a YAML manifestek is Gitben élnek (GitOps, ArgoCD, Kustomize). |
| **II.** | **Dependencies** | Minden függőséget explicit módon deklarálunk (`go.mod`, Dockerfile) és izolálunk (pl. Go vendoring), soha nem támaszkodunk a gazdagépre telepített globális csomagokra. |
| **III.** | **Config** | A környezetenként változó beállításokat szigorúan leválasztjuk a kódról, és környezeti változókban, ConfigMap-ben, illetve RBAC-védett Secret-ben tároljuk. |
| **IV.** | **Backing services** | A háttérszolgáltatásokat (adatbázis, kvstore, Redis, S3) csatolt erőforrásként kezeljük, URL/elérési cím és hitelesítő adatok segítségével, így kódmódosítás nélkül cserélhetők. |
| **V.** | **Build, release, run** | A fordítás (build), a konfigurációval való összecsomagolás (release – megváltoztathatatlan, egyedi azonosítóval) és a futtatás (run) fázisait szigorúan elkülönítjük. |
| **VI.** | **Processes** | Az alkalmazást egy vagy több állapotmentes (stateless, share-nothing) folyamatként futtatjuk; minden perzisztens adatot külső adattárolóba szervezünk ki. |
| **VII.** | **Port binding** | A szolgáltatást önállóan, HTTP porton keresztül exportáljuk beégetett IP-címek nélkül, így bármely szolgáltatás könnyen egy másik szolgáltatás háttérerőforrásává válhat. |
| **VIII.** | **Concurrency** | A terhelés növekedését horizontális skálázással (újabb Podok és folyamatok indításával) kezeljük a vertikális bővítés helyett. |
| **IX.** | **Disposability** | A gyors indítás és a kecses leállás (graceful shutdown: SIGTERM fogadása, új kérések elutasítása, futó kérések befejezése) biztosítja a rugalmas skálázást és a hibamentes frissítéseket. |
| **X.** | **Dev/prod parity** | A fejlesztői, teszt és éles környezeteket a lehető legközelebb tartjuk egymáshoz (CI/CD, DevOps, azonos típusú háttérszolgáltatások használata minden környezetben). |
| **XI.** | **Logs** | A naplókat folyamatos eseményfolyamként (event stream), pufferelés nélkül a szabványos kimenetre (stdout) írjuk; a gyűjtést és tárolást a platformra (`kubectl logs`) bízzuk. |
| **XII.** | **Admin processes** | Az egyszeri adminisztrációs feladatokat (adatbázis-migráció, tanúsítványcsere) pontosan ugyanazzal a kódbázissal, release-zel és konfigurációval futtatjuk, mint az éles folyamatokat. |

# 4. Tervezési tanulságok és a „13. faktor”

A service mesh és a Twelve-Factor App módszertan együttesen teszi lehetővé, hogy a mikroszolgáltatás-rendszerek hibatűrését, titkosítását és megfigyelhetőségét deklaratív módon, minimális alkalmazáskód-módosítással automatizáljuk.

Érdemes azonban szem előtt tartani az előadók által megfogalmazott **„13. faktort”** is: a nehézsúlyú cloud-native mintákat és infrastruktúra-rétegeket (Kubernetes, Service Mesh) csak akkor vessük be, ha a rendszer mérete és rendelkezésre állási igénye valóban indokolja, mert komoly üzemeltetési többletterhelést (overhead) jelentenek. Egy személyes bloghoz felesleges teljes service mesh-t építeni, ugyanakkor az olyan alacsony költségű tervezési mintákat, mint a tiszta konfigurációkezelés (manageability) és az alapvető időkorlátok/újrapróbálkozások, bármilyen Go alkalmazásban érdemes alapértelmezett jó gyakorlatként alkalmazni.
