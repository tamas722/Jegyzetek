Docker & OCI Rendszerarchitektúra

Kattints egy csomópontra a technikai részletekért

Docker CLI / Compose

User Space • REST Kliens

A docker parancssori kliens nem futtat konténereket közvetlenül: REST API kéréseket küld a /var/run/docker.sock UNIX domain socketen keresztül a háttérben futó dockerd démonnak.

curl --unix-socket /var/run/docker.sock http://localhost/v1.43/containers/json
Állásinterjú & Biztonsági tipp Soha ne csatold be a /var/run/docker.sock fájlt nem megbízható konténerbe, mert az teljes root jogosultságot ad a host felett!

containerd + containerd-shim

Container Runtime • Életciklus-kezelés

A containerd kezeli az image-ek letöltését (pull) és a konténerek életciklusát (K8s CRI kompatibilis). Minden elindított konténer mellé egy könnyűsúlyú containerd-shim folyamatot rendel, amely fenntartja a STDIO streameket és jelenti a kilépési kódot, így a Docker démon újraindításakor sem állnak le a futó konténerek.

ps aux | grep containerd-shim-runc-v2
Állásinterjú & Hibakeresési tipp A Kubernetes 1.24+ közvetlenül a containerd-t hívja CRI-n keresztül, kihagyva a Docker Engine réteget (dockershim kivezetése).

runc (OCI Low-Level Runtime)

OCI Runtime • Kernel Konfigurátor

Az Open Container Initiative (OCI) referencia-futtatója. Beolvassa a config.json specifikációt, meghívja a Linux kernel clone() és unshare() rendszerhívásait a névterekhez, beállítja a cgroups korlátokat és a pivot_root fájlrendszert, elindítja a konténer folyamatát, majd kilép.

runc spec && sudo runc run my-isolated-container
Állásinterjú & Hibakeresési tipp A runc nem marad futva a konténer teljes élete alatt: miután létrehozta a konténer folyamatot, átadja a vezérlést a containerd-shim folyamatnak.

Linux Namespaces (Izoláció)

Linux Kernel • Láthatósági Határ

Meghatározza, hogy mit láthat az adott folyamat a rendszerből. A 6+2 névtér (pid folyamatok, net hálózati interfészek, mnt csatolási pontok, uts hostnév, ipc memória, user UID/GID leképezés, cgroup) biztosítja a virtuális izolációt külön vendég-kernel nélkül.

lsns -p $(docker inspect -f '{{.State.Pid}}' my-app)
Állásinterjú & Hibakeresési tipp Distroless konténer hálózati hibakeresésekor nem kell telepíteni semmit az image-be: az nsenter -t <PID> -n netstat -tulnp paranccsal a hostról beléphetsz a konténer hálózati névterébe!

Control Groups (cgroups v2 Limitek)

Linux Kernel • Erőforrás Korlátozás

Meghatározza, hogy mennyi erőforrást használhat a konténer. A cpu.max túllépésekor a kernel CFS ütemezője visszafogja (throttling) a folyamatot, míg a memory.max túllépésekor a kernel OOM Killer azonnal lelövi a folyamatot (SIGKILL / Exit Code 137).

cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/memory.max
Állásinterjú & Hibakeresési tipp Az Exit Code 137 (128 + 9 SIGKILL) szinte mindig OOM Killert jelent, míg az Exit Code 143 (128 + 15 SIGTERM) szabályos leállítást jelez.

OverlayFS (overlay2 tároló-meghajtó)

Linux Kernel • Union Filesystem

Egyesíti a csak olvasható (Read-Only) image rétegeket (lowerdir) és a konténer saját írható-olvasható (upperdir) rétegét egyetlen merged nézetben. Módosításkor Copy-on-Write (CoW) mechanizmussal felmásolja a fájlt az upperdir rétegbe; a perzisztens adatokhoz Docker Volume csatolás szükséges.

docker inspect -f '{{.GraphDriver.Data.MergedDir}}' my-app
Állásinterjú & Hibakeresési tipp Ha egy Dockerfile-ban egy nagy fájlt letöltesz egy RUN lépésben, majd egy következő RUN rm lépésben törlöd, az image mérete NEM csökken — csak egy whiteout fájl jön létre a felső rétegben!

.dockerignore szűrés

Build Context • Sebesség & Biztonság

A docker build indításakor a CLI összecsomagolja az aktuális könyvtárat (Build Context) és elküldi a démonnak. A .dockerignore megakadályozza, hogy a lokális node_modules, .git történet vagy érzékeny .env kulcsok bekerüljenek az image-be vagy invalidálják a réteg-gyorsítótárat.

# .dockerignore .git node_modules .env* dist *.log
Állásinterjú & Hibakeresési tipp Ha a COPY . . minden apró lokális fájlra invalidálja a cache-t vagy gigabájtos contextet küld, mindig a .dockerignore hiánya az elsődleges ok.

Stage 1: Builder Image

Multi-Stage Build • Layer Cache Optimalizálás

Az első szakasz tartalmazza a fordítókat (TypeScript, GCC, devDependencies). Először kizárólag a package*.json fájlokat másoljuk be és futtatjuk az npm ci parancsot: így a függőségek rétege cache-elve marad, amíg a package-lock.json nem változik, még ha a forráskód módosul is.

FROM node:20-bookworm-slim AS builder WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build && npm prune --production
Állásinterjú & Hibakeresési tipp Az utasítások sorrendje kritikus: a ritkán változó rétegek (függőségek) kerüljenek előre, a gyakran változó forráskód (COPY src/) pedig a Dockerfile végére.

COPY --from=builder (Artefaktum átadás)

Multi-Stage Build • Támadási Felület Csökkentése

A két build-szakasz közötti tiszta határvonal: kizárólag a lefordított dist/ könyvtárat és a production node_modules csomagokat emeljük át az új, tiszta alap-image-be. A fordítóeszközök, forráskódok és köztes cache-ek a Builder rétegben maradnak és nem kerülnek a végső image-be.

COPY --from=builder --chown=node:node /app/dist ./dist COPY --from=builder --chown=node:node /app/node_modules ./node_modules
Állásinterjú & Hibakeresési tipp A --chown=node:node kapcsolóval már másoláskor beállítod a jogosultságot, így elkerülhető egy extra RUN chown -R réteg, ami megduplázná az image méretét!

Stage 2: Production Runner

Production Hardening • PID 1 & Non-Root

A végső futtatókörnyezet minimalista, nem-root felhasználóval (USER node) fut, és tini-t használ ENTRYPOINT-ként (PID 1), hogy a SIGTERM leállítási jelek célba érjenek és a zombi folyamatok felszabaduljanak.

FROM node:20-bookworm-slim AS runner RUN apt-get update && apt-get install -y --no-install-recommends tini && rm -rf /var/lib/apt/lists/* USER node ENTRYPOINT ["/usr/bin/tini", "--"] CMD ["node", "dist/main.js"]
Állásinterjú & Hibakeresési tipp Mindig exec formát (["node", "dist/main.js"]) használj shell forma helyett, különben a /bin/sh -c lesz a PID 1, amely nem továbbítja a SIGTERM jelet az alkalmazásnak!

Külvilág (80/443 TCP Ingress)

Hálózati Határ • Port Publikálás

Éles környezetben kizárólag a Reverse Proxy 80/443-as portja publikus a host interfészén. Sem az alkalmazás, sem az adatbázis nem használ ports: direktívát a külső hálózat felé.

# Csak lokális teszteléshez köss belső szolgáltatást localhostra: ports: - "127.0.0.1:27017:27017" # Nem 0.0.0.0:27017!
Állásinterjú & Biztonsági tipp A Docker a 0.0.0.0 portpublikálásnál közvetlenül a PREROUTING iptables láncba ír, ezzel megkerüli az alapértelmezett ufw tűzfalszabályokat a hoston!

Traefik / Nginx Reverse Proxy

Ingress Gateway • frontend-net

A frontend-net egyedi bridge hálózaton keresztül éri el az alkalmazást a Docker beépített DNS-szervere (127.0.0.11) segítségével, konténernév alapján (http://my-app:3000). A backend-net hálózathoz nincs csatlakoztatva, így kompromittálódás esetén sem látja az adatbázist.

services: proxy: image: traefik:v3.0 ports: ["80:80", "443:443"] networks: ["frontend-net"]
Állásinterjú & Hibakeresési tipp Az alapértelmezett bridge hálózat nem támogatja az automatikus névfeloldást (Service Discovery) — mindig egyedi, felhasználó által definiált bridge hálózatot használj!

Alkalmazás Konténer (my-app)

Hardened Workload • Kettős Hálózat

A my-app mindkét hálózathoz (frontend-net és backend-net) csatlakozik. A konténer fájlrendszere írásvédett (read_only: true), minden Linux kernel capability el van véve (cap_drop: [ALL]), és az ideiglenes fájlok memóriába (tmpfs: /tmp) íródnak.

services: my-app: read_only: true tmpfs: ["/tmp"] cap_drop: ["ALL"] security_opt: ["no-new-privileges:true"] networks: ["frontend-net", "backend-net"]
Állásinterjú & Biztonsági tipp A read_only: true + cap_drop: ALL kombináció megakadályozza, hogy egy RCE sérülékenységgel a támadó binárisokat módosítson vagy jogosultságot emeljen a konténerben.

Adatbázis (MongoDB + Named Volume)

Data Tier • Zárt backend-net

Kizárólag az internal: true jelölésű backend-net hálózaton ül, amelynek nincs alapértelmezett átjárója (default gateway) a külvilág felé. Az adatok perzisztenciáját az OverlayFS-t megkerülő Named Volume (mongo-data:/data/db) biztosítja.

networks: backend-net: driver: bridge internal: true # Nincs kimenő internet / külső elérés
Állásinterjú & Hibakeresési tipp Adatbázisoknál mindig Named Volume-ot használj Bind Mount helyett, mert a Volume megőrzi a konténer belső UID/GID jogosultságait és natív I/O sebességgel ír a host fájlrendszerre.
